# 06 · 开放问题与待测项

按「阻塞程度」排序。前 3 条决定实现形态，建议动手写代码前先测掉。

## 1. 🔴 `blit` 是否接受 raw 字节串（而不是表）

**为什么重要**：`docs/02` §7。若接受字符串，每像素 0.17 µs 的「串→表」成本消失，
320×180 的处理从 ~18 ms 降到 ~8 ms，**预算翻倍**，可以支持更大的区域或 P2 profile。

**怎么测**：

```lua
local h = peripheral.find("hologram")
local s = string.rep("\0", 64*64)              -- 纯黑
local t = {}; for i = 1, 64*64 do t[i-1] = 0 end

local t0 = os.clock(); h.blit(0, 0, 64, 64, t); local dtTab = os.clock() - t0
local t1 = os.clock(); local ok, err = pcall(h.blit, h, 0, 0, 64, 64, s); local dtStr = os.clock() - t1
print(ok, err, dtTab, dtStr)
```

**判据**：`ok == true` 且画面正确 ⇒ 用字符串。否则维持表。

**若支持**：`docs/03` §3 的 `cur` 可以整个省掉，直接「拼字符串→一次 blit」，P1 每帧成本接近 0.6 ms/块。

---

## 2. 🔴 P1（64×64）的观感是否可接受

**为什么重要**：决定要不要立刻上 P2。P1 实现简单、成本低，但运动粒度粗。

**怎么测**：离线转一段「固定机位 + 人物走动」和一段「摄像机平移」的 P1 `.ccv`，
在真实屏幕上看（或把帧导出成 PNG 看）。

**判据**：
- 平移类 → 应该很好（整块 MV 正好）；
- 固定机位 + 局部运动 → 会出现 64 px 块状。若不可接受，直接做 P2（16×16），别浪费时间优化 P1。

**顺带决策**：是否需要「两级 MV」（先 64×64 判断动没动，动了再按 16×16 细分）。

---

## 3. 🔴 `cur` 用「整串」还是「按行表」

**为什么重要**：`docs/03` §3。整串拼接每次 57.6 KB 拷贝；按行表每次 320 B。
但按行表在 MV 拷贝时要同时改「源行」和「目标行」，逻辑复杂、易错。

**怎么测**：微基准 —— 在 320×180 的串上改 64 行 × 64 B，对比两种表示的耗时。

**判据**：整串 ≤ 1 ms 就用整串（简单优先）；否则用按行表。

---

## 4. 🟡 编码器用 Node 还是 ffmpeg 滤镜

- **A. 纯 Node 手写编码器**：完全可控、可位精确校验、无外部依赖。慢（但离线转码不需要快）。
- **B. ffmpeg 先转成 rawvideo，Node 再做块级分析**：省掉解码视频的活，仍要自己找 MV。
- **C. ffmpeg 直接输出某种粗粒度运动信息**：没有现成滤镜能给出「64×64 块是否相同/平移多少」，不可行。

**建议 A**（ffmpeg 只负责解出 rgb24 raw，Node 做分块/匹配/打包）。这与「编码器必须与解码器一致」的要求最合。

---

## 5. 🟡 帧率与分辨率的目标值

- 640×360@20 是上一代达到过的值，但那需要 4 台 raw 渲染机 + 宿主机转码。
- 本版每台还要解码。按 `docs/02` 的预算（典型帧 7 ms）应该仍能 20 fps，但**未实测**。
- 需要跑一次「解码+blit+ack」的合成基准，确定单机能到多少 fps，再决定是否降到 15。

**待定**：
- 目标 fps：20（保守 15）？
- 单 quadrant 尺寸：320×180（保守）还是 480×270（激进，成本 ×2.25）？

---

## 6. 🟡 master 的 ack 屏障放 Node 还是 fabric

`docs/04` §3.1 的 (a)/(b)。第一版建议 Node 锁步（简单），但 Node 需要知道「这个 room 应该有 4 台」：

- 靠 `HELLO` 时上报的 `region` 集合推断？还是配置文件显式声明「wall1 有 4 个 quadrant」？
- **建议**：配置文件声明 wall 的网格（2×2），Node 只发帧给「已连接的那个 quadrant」，缺一台就整个 room 暂停等它。

---

## 7. 🟡 音频（第二版）

- 上一代的方案：独立音频机 + `role=audio` + CEE `getSpeakers(pin).playAudio(s8 tbl, vol)`，48 kHz。
- 32 KB/s（8-bit 48k 单声道）对 ws 不是问题。
- **待定**：音频与画面的对齐由谁负责（Node 按帧配对 vs CC 侧自己缓冲）？上一代是 Node 配对 + CC 丢弃 2 s 以上积压。

---

## 8. 🟢 要不要 GUI

上一代的 GUI（库/缩略图/进度条）踩了很多坑（`hologram` 主线程调用吞事件、framebuffer 泄漏、
中文必须 `\uXXXX`、`drawText` 第 5 参是字体名）。第一版**不做**，用 Node 侧配置切换视频。

---

## 9. 🟢 版本与兼容策略

- 码流 `version` 升级时，CC 端是否要保留旧解码器？
- **建议**：不保留。单人项目，宁可让 CC 明确报错「协议版本不匹配」，也不要维护双路径。

## 10. 🟢 是否复用上一代的代码

| 上一代文件 | 可复用性 |
|---|---|
