# 06 · 开放问题与待测项

> 2026-11-15 修订：架构已定为**一块 640×360 屏 + 一台电脑**（[ADR-0007](adr/0007-一块全息屏只能接一台电脑.md)）。
> 原先的阻塞项（多机共享外设）已由反编译解决。以下是**实现后用真机校准**的事项。

## 1. 🔴 单次 `blitFrameBufferArea` 的真实耗时

**为什么重要**：`docs/02` §5 的块大小选择（16×16，920 块，估算 9.2 ms）全靠「~10 µs/次」这个假设。
若实际是 50 µs，920 块就是 46 ms，必须退到 32×32（240 块）。

**怎么测**：真机上跑 920 次空转的 `blitFrameBufferArea`，`os.clock()` 夹住，重复 20 次取中位数。

**判据**：< 20 µs ⇒ 16×16；20–60 µs ⇒ 32×32；> 60 µs ⇒ 64×64。

> MVP 先按 16×16 实现；`HELLO.block` 是运行期参数，改块大小不需要改代码。

## 2. 🔴 `sync()` 的 zlib 压缩成本

`HoloSyncData.compress` 用 `Deflater` 压**整个** 230400 B 缓冲，无法只压变化区域。

**要测**：640×360 缓冲 sync 一次实际多久。若 > 5 ms，20 fps 下就是 10% 开销，
且它与 RAW 成本叠加。届时要么降帧率，要么拆两块屏。

**MVP 日志里会记录 `sync_ms`**，跑一次就知道。

## 3. 🟡 16×16 块的观感

**怎么测**：转好 `科学-MIMI.mp4` 后在真实屏幕上看。

**判据**：
- 平移/摇镜 → 应该很好（MV 覆盖）；
- 快速运动/局部动作 → 可能出现 16 px 块状与「块错位」。
- 若不可接受，先试 8×8（3600 块 × 10 µs = 36 ms，超预算）⇒ 不可行。
  **所以 16×16 基本是画质下限**，要更好只能上残差（本项目不做）。

## 4. 🟡 编码器的块匹配策略

MVP 用最笨的：**对每个块，在 ±8 像素范围内穷举搜索 SAD，取最小**。

- 复杂度：920 块 × 17×17 个候选 × 256 像素 = 6.8×10⁷ 次比较/帧。离线转码可接受（几秒/帧）。
- 优化方向（都不影响码流格式）：三层步长搜索、零 MV 优先、SAD 早退。

**待定**：RAW/MV 的判决阈值。太松 ⇒ 码率爆炸；太紧 ⇒ 画质糊。
**建议**：`SAD_mv + 50 > SAD_raw` 时选 RAW（需实测调）。

## 5. 🟡 帧率与分辨率

- 640×360@20 是设计目标，按预算应能达到，**未实测**。
- `科学-MIMI.mp4` 是 1280×720@24fps、188 s。转成 640×360@20 后有 3760 帧。
- 若单帧成本超预算，优先级：降 fps（20→15）> 降分辨率（640×360→480×270）> 换块大小。

## 6. 🟡 渐进刷新的阈值

`docs/02` §6 建议把全 RAW 帧拆成 3 帧。但**什么时候触发**？

- 按「RAW 像素占比」触发？还是按「本帧估算耗时 > 预算」？
- 建议：编码器按**预算**判断（`estimated_ms > 35` 就拆），而不是按占比。
