## 1. 🔴🔴 4 台电脑是否共享同一个 hologram 外设实例

**这是当前唯一的阻塞项，且只能用真机确认。**

若 4 台通过 CEE 数据网络访问**同一台** hologram，则 `HoloFrameBufferManager` 的这些字段是共享的：

| 共享字段 | 后果 |
|---|---|
| `currentActivated` | 「当前激活缓冲」是**一个**字段 ⇒ A 机 `activateFrameBuffer(-1)` 会改变 B 机下一次 `blit` 的目标 ⚠️⚠️ |
| `buffers[16]` | 4 台各占一个 id，`releaseAllFrameBuffer()` 会清掉别人的 ⚠️ |
| `te.buffer` | 显示缓冲本来就共享（拼接依赖它）✅ |
| `te.dirty` / `waitToSend` | 只由 master `sync`，无冲突 ✅ |

**怎么测**（4 台各跑一遍）：

```lua
local h = peripheral.find("hologram") or cee.getPeripherals(...)[1]
print("maxBuf", h.getMaxBufferSize())
print("allocd", textutils.serialise(h.getAllocatedFrameBuffers()))
local id = h.allocateFrameBuffer(320, 180)
print("myId", id)                      -- 4 台拿到的 id 是否连续且互不相同？
```

然后在 A 机执行 `h.activateFrameBuffer(-1)`，B 机立刻执行一次 `h.blit(...)`，
看它画到的是显示缓冲还是 prev 缓冲。

**判据**：4 台看到的 `getAllocatedFrameBuffers()` 若包含别人分配的 id ⇒ 共享实例。

### 若确认共享，三条退路

| 退路 | 说明 | 代价 |
|---|---|---|
| **A. 单机负责整个 640×360** | 按 `docs/02` §5：典型约 12 ms、全 RAW 约 72 ms（超预算，但全 RAW 只在场景切换出现）。可配合「关键帧跨 2 帧发送」。 | 架构最简；一台电脑扛全部 |
| **B. 每台配独立 hologram + 物理拼接** | framebuffer 不再共享，退化成「多块屏」。 | 跨屏同步多一层（`04` §5） |
| **C. 不分配 framebuffer，退回 Lua 侧 prev** | 成本回到 `1.3 ms/块`（RAW 级），只能用 64×64 块且预算紧张。 | 画质与帧率都退步 |

**建议**：先测。若共享，优先 B（保留 4 台分工，且 framebuffer 天然隔离），
其次 A（若只想要「能播」）。

## 2. 🟡 16×16 的调用开销是否如估算（~10 µs）

**为什么重要**：`docs/02` §5 的块大小选择全靠这个数。若单次 `blitFrameBufferArea`
实际要 50 µs，240 块就是 12 ms，需要退到 32×32（60 块 ≈ 3 ms）。

**怎么测**：真机上跑 240 次 `blitFrameBufferArea`，`os.clock()` 夹住，重复 20 次取中位数。

**判据**：< 15 µs ⇒ 16×16；15–40 µs ⇒ 32×32；> 40 µs ⇒ 64×64。

> 纯读字节码只能知道它是「逐字节循环」，不知道 JVM 上实际多久——这个必须实测。
> 但**不需要写完整解码器**，一个 20 行的循环就能测。

## 3. 🟡 `RAW` 建表与 `blit` 的实测比例

`docs/02` §1 的 0.17 / 0.14 µs/像素是在 320×180 整屏测的。
16×16 的小表（256 项）可能有不同的常数开销（每次 `blit` 的固定成本）。

**怎么测**：分别用 256 / 1024 / 4096 项的块重复调用，拟合出「每像素 + 每次调用」两个常数。

**判据**：若固定开销明显（> 0.2 ms/次），说明小块吃亏，需要重新算 §5 的甜点。

## 4. 🟡 编码器用 Node 还是 ffmpeg 滤镜

- **A. 纯 Node 手写**：完全可控、可位精确校验、无外部依赖。慢（离线转码不在乎）。
- **B. ffmpeg 出 rawvideo，Node 做分块与块匹配**：省掉解容器的活，仍要自己找 MV。
- **C. ffmpeg 直接给运动信息**：没有现成滤镜能给出「16×16 块是否相同 / 平移多少」，**不可行**。

**建议**：ffmpeg 只负责 `-f rawvideo -pix_fmt rgb24` 到管道，其余全在 Node 里做。

## 5. 🟡 帧率与区域尺寸的目标值

- 640×360@20 是上一代达到过的值（4 台 raw 渲染机 + 宿主机转码）。
- 本版每台还要解码。按新成本模型（`docs/02` §5）单 quadrant 约 5 ms，**应该**能 20 fps，但未实测。
- **待定**：20 fps（保守 15）？单 quadrant 320×180（保守）还是 480×270（激进）？

## 6. 🟡 master 的 ack 屏障放 Node 还是 fabric

`04` §3.1 的 (a)/(b)。第一版建议 Node 锁步（简单），但 Node 要知「这个 room 应有几台」：

- 靠 `HELLO` 上报的 `region` 集合推断？还是配置文件显式声明网格？
- **建议**：配置文件声明 wall 的网格（2×2），缺一台就整个 room 暂停等它。

## 7. 🟡 `sync` 的 zlib 压缩成本

`HoloSyncData.compress` 用 `Deflater` 压**整个** 230400 B 缓冲，无法只压变化区域。

**要测**：640×360 缓冲压缩一次实际多久（1 ms？3 ms？）。20 fps 下若 > 5 ms 就成瓶颈，
此时要么降帧率，要么把墙拆成两块 hologram（各自 sync）。

## 10. 🟢 版本与兼容策略
