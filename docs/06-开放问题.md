# 06 · 开放问题与待测项

> 2026-11-15 修订：架构已定为**一块 640×360 屏 + 一台电脑**（[ADR-0007](adr/0007-一块全息屏只能接一台电脑.md)）。
> 原先的阻塞项（多机共享外设）已由反编译解决。以下是**实现后用真机校准**的事项。

## 1. 🔴 单次 `blitFrameBufferArea` 的真实耗时

**为什么重要**：`docs/02` §5 的块大小选择（16×16，920 块，估算 9.2 ms）全靠「~10 µs/次」这个假设。
若实际是 50 µs，920 块就是 46 ms，必须退到 32×32（240 块）。

**怎么测**：真机上跑 920 次空转的 `blitFrameBufferArea`，`os.clock()` 夹住，重复 20 次取中位数。

**判据**：< 20 µs ⇒ 16×16；20–60 µs ⇒ 32×32；> 60 µs ⇒ 64×64。

> MVP 先按 16×16 实现；`HELLO.block` 是运行期参数，改块大小不需要改代码。

## 2. 🔴 `sync()` 的 zlib 压缩成本

`HoloSyncData.compress` 用 `Deflater` 压**整个** 230400 B 缓冲，无法只压变化区域。

**要测**：640×360 缓冲 sync 一次实际多久。若 > 5 ms，20 fps 下就是 10% 开销，
且它与 RAW 成本叠加。届时要么降帧率，要么拆两块屏。

**MVP 日志里会记录 `sync_ms`**，跑一次就知道。

## 3. 🟡 16×16 块的观感

**怎么测**：转好 `科学-MIMI.mp4` 后在真实屏幕上看。

**判据**：
- 平移/摇镜 → 应该很好（MV 覆盖）；
- 快速运动/局部动作 → 可能出现 16 px 块状与「块错位」。
- 若不可接受，先试 8×8（3600 块 × 10 µs = 36 ms，超预算）⇒ 不可行。
  **所以 16×16 基本是画质下限**，要更好只能上残差（本项目不做）。

## 4. 🟡 编码器的块匹配策略

MVP 用最笨的：**对每个块，在 ±8 像素范围内穷举搜索 SAD，取最小**。

- 复杂度：920 块 × 17×17 个候选 × 256 像素 = 6.8×10⁷ 次比较/帧。离线转码可接受（几秒/帧）。
- 优化方向（都不影响码流格式）：三层步长搜索、零 MV 优先、SAD 早退。

**待定**：RAW/MV 的判决阈值。太松 ⇒ 码率爆炸；太紧 ⇒ 画质糊。
**建议**：`SAD_mv + 50 > SAD_raw` 时选 RAW（需实测调）。

## 5. 🟢 帧率与分辨率（已实测）

- 640×360@20 **已在真机 #81 跑通**：连续 2700+ 帧无崩溃、无丢分片，稳定播放。
- `科学-MIMI.mp4` 是 1280×720@24fps、188 s。转成 640×360@20 后有 3762 帧 / 4729 条消息 / 71.4 MB。
- 实测瞬时速率 ~21 fps（片源 20 fps），差值是日志按 20 帧打点 + 4 ms 发送定时的量化误差，不是累积漂移。
- 若仍想降负载，优先级：降 fps（20→15）> 降分辨率（640×360→480×270）> 换块大小。

## 6. 🟡 渐进刷新的阈值

`docs/02` §6 建议把全 RAW 帧拆成 3 帧。但**什么时候触发**？

- 按「RAW 像素占比」触发？还是按「本帧估算耗时 > 预算」？
- 建议：编码器按**预算**判断（`estimated_ms > 35` 就拆），而不是按占比。

## 10. 已解决（存档）

| 原问题 | 结论 |
|---|---|
| `blit` 是否接受 raw 字节串？ | **不接受**（`getTable(4)`）。但不需要——MV 走 `blitFrameBufferArea` |
| MV 要不要用 Lua 拼字符串？ | **不要**。Java 侧 memcpy，快约 100 倍（ADR-0006） |
| 4 台能否共享一块 hologram？ | **不能**，`currentActivated` 是共享单字段（ADR-0007） |
| 需不需要 fabric 做 ack 栅栏？ | 单机**不需要**（`docs/04` §2） |
| 码流要不要 DCT/熵编码？ | **不要**，Lua 解不动（ADR-0002/0003） |
| 包结构要不要 workspace？ | **不要**，单包 `private`（ADR-0005） |
| `max_websocket_message` 够不够？ | **够**。实测 64 KB 二进制帧收发正常，配置 131072；`MAX_MSG` 取 48 KB 留足余量 |
| CC 收不到大消息？ | **不是**大小问题，是**开播时机**。服务器必须在收到 `READY(0x02)` 后才发第一帧，否则首帧在 `resize()` 期间被丢弃（见下「踩坑记录」） |
| 控制消息能否用 `ws.send(str)`？ | **不能**。Lua 侧只有 `send/close/receive/getResponseHeaders`，没有 `sendBinary`；**二进制要靠 `send(msg, true)`**。用默认的 text 帧发二进制，服务端 ws 会按 UTF-8 校验并把 ≥0x80 的字节改写成 U+FFFD，ACK 就会变成 `status=191 decode=48384` |
| 码流里块记录要按 index 升序吗？ | **必须**。线上不传块号，解码端按位图升序与负载顺序配对。渐进刷新把一帧拼成「先全部 MV 再全部 RAW」，不排序就会把 MV 挂到错误的块上，在真机上表现为 `ArrayIndexOutOfBoundsException` |

## 11. 踩坑记录（真机联调）

按发现顺序，全部已修，留档避免重犯。

| 现象 | 真因 | 修法 |
|---|---|---|
| `out of space` | 机架式电脑只有 **4 KB** 磁盘，`computer_space_limit` 管不到 | `padsize` 稀疏文件充值（`docs/05` §3.2） |
| `run error: bad argument (string expected, got boolean)` | `websocket_message` 的参数是 `(address, message, isBinary)`，消息在**第 2 个** | 取 `p2`；反编译 `WebsocketHandler` 确认 |
| `ArrayIndexOutOfBoundsException: Index -6171` | 两处：①编码器 `sadAt` 用带 stride 的采样，只检查采样点，边缘块越界候选能通过；②一帧拆多片时块记录未按 index 排序 | ①`mvInBounds` 整矩形预检 + 末端断言；②`encodeFramePart` 内 `sort` |
| 首帧丢失、画面从错位开始 | 服务器发出 HELLO 后 4 ms 就开播，此时 CC 还在 `resize()`/`allocateFrameBuffer()` | 客户端就绪后发 `READY(0x02)`，服务器门控；另设 3 s 兜底 |
| `ack status=191 decode=48384ms` | ACK 用 text 帧发出，服务端按 UTF-8 校验把 `0xBD` 改成替换符 | `ws.send(msg, true)` |
| 参考解码器「位精确」却和真机不一致 | ①`applyFrame` 对越界 MV 静默钳到 0，掩盖了编码器 bug；②校验器每收到一个 ws 分片就推进 `prev`，而真 CC 只在**整帧收齐**后 `snapshot` | ①越界直接抛错，镜像真机行为；②按 `part == parts-1` 才推进 |

**方法论教训**：`transcode` 的自检必须跑在**即将发送的字节**上（`decodeFrame(p)`），
而不是编码器的内存对象——线上格式不含块号，内存检查看不见「排序错」这一整类 bug。
另外，真机是最快的校验器：把整段 188 s 丢给 fengari 要跑十几分钟，而真机 3 分钟就放完了。
