# 01 · 码流格式（ccv v1）

## 1. 传输层

- **载体**：CC `http.websocket`（`ws://` 内网调试 / `wss://` 公网）。二进制消息，**不用文本/JSON**（解析成本高）。
- **方向**：服务器 → CC 是主流（帧 + 控制）；CC → 服务器只有 ack / 上报。
- **单消息上限**：
  - CC 侧硬上限 `max_websocket_message = 131072` 字节（`config/computercraft-server.toml` 的 `*` 规则）→ 留余量按 **< 64 KB** 设计。
  - 第一版尺寸下**一帧 = 一条消息**：
    - P1 quadrant 最坏（15 块全 RAW）= 15×4096 + 12 ≈ **61.5 KB** ✅
    - P2 quadrant 最坏（240 块全 RAW）= 240×256 + 36 ≈ **61.5 KB** ✅
  - 若将来单机负责更大区域（> 64 KB/帧），按 `0x11 CONT` 分片，见 §6。
- **鉴权**：URL 里带 `?token=<room_secret>`；服务器按 token 决定 room 与 region。

## 2. 消息类型总表

| 码 | 方向 | 名字 | 用途 |
|---|---|---|---|
| `0x01` | S→C | `HELLO` | 协商版本 / 分区 / 尺寸 / fps |
| `0x02` | C→S | `READY` | CC 报能力与自检结果 |
| `0x10` | S→C | `FRAME` | 一帧的瓦片数据 |
| `0x11` | S→C | `CONT` | 大帧的后续分片（>64 KB 时才用） |
| `0x13` | C→S | `ACK` | 某帧已画完（含耗时） |
| `0x14` | S→C | `CONTROL` | play / pause / seek / fps / stop |
| `0x20` | C→S | `STATS` | 周期上报：帧率、解码耗时、丢帧 |
| `0x30` | S→C | `PING` | 保活（防 CC 事件被吞后彻底静默） |
| `0x31` | C→S | `PONG` | 回 PING |

所有多字节整数 **大端**（与上一代的 `x*256+y` 读法一致，CC 端 `string.byte` 顺读即可）。
有符号量（运动矢量）用 **`u8` + 偏移 128** 表示（`实际值 = byte - 128`），避免 Lua 的位运算/符号处理。

## 3. `HELLO`（0x01）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8 | `type` | `0x01` |
| 1 | u8 | `version` | 协议版本，当前 **1**；不为 1 则 CC 直接退出并打印错误 |
| 2 | u8 | `profile` | `1`=P1(64×64) / `2`=P2(16×16) |
| 3 | u8 | `fps` | 目标帧率 |
| 4 | u16 | `wall_w` | 整墙宽（如 640） |
| 6 | u16 | `wall_h` | 整墙高（如 360） |
| 8 | u16 | `region_x` | 本机负责区域左上角（全局坐标） |
| 10 | u16 | `region_y` | 同上 |
| 12 | u16 | `region_w` | 区域宽（如 320） |
| 14 | u16 | `region_h` | 区域高（如 180） |
| 16 | u8 | `flags` | bit0=`1` 表示本机是 master（要负责 sync） |
| 17 | u8 | `name_len` | room 名长度 |
| 18 | … | `name` | room 名（ASCII） |

CC 收到后：`resize(wall_w, wall_h)`、`setColorMapping(...)`、记下 `region_*`。

## 4. `FRAME`（0x10）—— P1 版本

```
+0   u8   type      = 0x10
+1   u16  seq       帧号（回绕到 0 之后重新计数；CC 只需与上一帧比较是否连续）
+3   u8   flags     bit0 = KEY（本帧不依赖上一帧）
                    bit1 = DUP（整帧与上一帧相同，后面没有数据）
                    bit2 = DROP_OK（CC 可丢弃本帧而不影响后续，通常 = !KEY）
+4   u8   tiles_x   本区域每行瓦片数（320/64 = 5）
+5   u8   tiles_y   本区域瓦片行数（180/64 = 3）
+6   bitmap[⌈tx*ty/8⌉]   每 bit 对应一个瓦片（行优先），1 = 有数据
+…   依次处理每个 bit=1 的瓦片（行优先顺序）：
       u8  mode
            1 = MV   （运动补偿拷贝）
            2 = RAW  （完整 64×64 像素）
       mode=1: i8 dx, i8 dy   （见 §4.1）
       mode=2: 4096 字节像素（行优先，每像素 1 字节 = RRGGBBAA 各 2 bit 的打包值）
```

`KEY` 帧里所有 `bit=1` 的瓦片必须是 `RAW`（不能用 MV）。

### 4.1 MV 的精确语义（编解码必须一致）

设本瓦片在区域内的位置是 `(bx, by)`，尺寸 `64×64`，`prev` 是**上一帧的完整区域**（320×180 字符串，行优先）。

```
对瓦片内每个 (x, y)，0 ≤ x < 64，0 ≤ y < 64：
    sx = bx + x + dx
    sy = by + y + dy
    if 0 ≤ sx < region_w and 0 ≤ sy < region_h:
        cur[bx+x, by+y] = prev[sx, sy]
    else:
        cur[bx+x, by+y] = 0        ← 越界补黑，无边缘延拓、无插值
```

- `dx, dy` 是**整数**、可以是负、范围 `-128..127`（编码器保证不越界到无意义区）。
- **拷贝源是上一帧**（不是当前帧），所以同一帧内多个 MV 瓦片互不影响、顺序无关。
- 没有亚像素、没有残差、没有边界滤波。

### 4.2 `RAW` 的像素编码

每像素 1 字节，值 `v` 解成四个 2-bit 通道：`R=(v>>6)&3, G=(v>>4)&3, B=(v>>2)&3, A=v&3`，
再经 `setColorMapping(c0,c1,c2,c3)` 映射到 0–255。这与上一代 `player.lua` 的打包方式**完全一致**，
也是 hologram `blit` 直接吃的格式。

## 5. 其它消息

### `ACK`（0x13，C→S）

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u8 | `type` = 0x13 |
| 1 | u16 | `seq` |
| 3 | u8 | `status`：0=ok，1=慢（本帧解码超预算），2=错（附 `u8 errcode`） |
| 4 | u16 | `decode_ms`（可选，用于服务器自适应降帧） |

### `CONTROL`（0x14，S→C）

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u8 | `type` = 0x14 |
| 1 | u8 | `cmd`：0=play，1=pause，2=seek，3=set_fps，4=stop |
| 2 | u32 | `arg`（seek=毫秒；set_fps=fps） |

### `STATS`（0x20，C→S）

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u8 | `type` = 0x20 |
| 1 | u16 | 最近 1 s 的帧数 |
| 3 | u16 | 平均 `decode_ms` |
| 5 | u16 | 累计丢帧 |
| 7 | u8 | 剩余内存/状态位（调试用） |

### `PING`/`PONG`（0x30/0x31）

`PING` 每 200 ms 发一次，内容为空。CC 必须回 `PONG`。
**为什么需要**：CC 调用 hologram 的主线程 API 时会吞掉排队事件（上一代 `docs` 里记了多条实测），
一个纯 timer 驱动的循环可能「静默」。周期消息是让事件循环持续转动的可靠手段。

## 6. 分片（`CONT`，0x11）—— 仅当单帧 > 64 KB

```
+0 u8  type = 0x11
+1 u16 seq
+3 u8  part     分片序号，从 0 开始
+4 u8  parts    总分片数
+5 …   紧接 FRAME 消息去掉前 1 字节后的对应切片
```

CC 端把切片按 `part` 拼回一条完整 `FRAME` 再解。第一版尺寸下不会用到。

## 7. 容器格式 `.ccv`（离线文件）

```
0   4B  magic "CCV1"
4   u8  profile
5   u8  fps
6   u16 wall_w
8   u16 wall_h
10  u8  tiles_x
11  u8  tiles_y
12  u32 frame_count
16  u32 index_offset      （相对文件头）
20  u32 duration_ms
24  …   预留 8 字节
--
file[index_offset] = frame_count 条索引，每条：
    u32 offset
    u16 length
    u16 seq
--
每个 frame 的数据就是 §4 的 `FRAME` 消息（去掉开头的 type 字节，或保留，二者选一，编码器决定时写进 ADR）
```

**每个 quadrant 一个 `.ccv`**（因为 MV 不能跨区域），文件名 `xxx.q0-0.ccv` … 或统一放在一个文件里按 region 分段。
第一版：**一个视频 = 一个目录，里面 4 个 .ccv + 一个 `meta.json`**，简单、可 diff、可单独替换。

## 8. 版本与兼容

- `version` 只在不兼容时 +1；CC 端遇到未知版本**拒绝并打印**，不要「尽力解析」。
- 新增模式（例如 `mode=3` 表示 8×8 子块 MV）属于**兼容扩展**：CC 不认识的 mode 必须
  按 `RAW` 的等价方式失败退出（不能静默画错），由 `HELLO.version` 之外的 `caps` 位协商（第二版再加）。
- 字节序固定大端；不做主机序探测。

## 9. 一个完整的例子（P1，单瓦片 MV）

假设区域 320×180（`tiles_x=5, tiles_y=3`，共 15 个瓦片 → bitmap 占 `⌈15/8⌉ = 2` 字节），
第 7 帧只有 (0,0) 与 (64,0) 两个瓦片有数据，前者 RAW、后者右移 2 px：

```
10 00 07 02 05 03 03 00       ← FRAME: type=10 seq=7 flags=02(DROP_OK) tx=5 ty=3 bitmap=0b0000_0011 0000_0000
02 <4096 bytes>               ← 瓦片0: RAW
01 82 00                      ← 瓦片1: MV dx=+2 dy=0   (0x82=130 → 130-128=+2)
```

`DUP` 帧（整帧不变）只有 6 字节：`10 00 07 04 05 03`（无 bitmap）。
静止画面时这就是每帧的全部流量。
