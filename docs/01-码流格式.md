# 01 · 码流格式（ccv v1）

> 2026-11-15 定稿：默认块 **16×16**，整墙一个 region（`0,0,640,360`），
> 大帧用 `part`/`parts` 分片（取消了独立的 `CONT` 消息）。依据 [`adr/0006`](adr/0006-MV用帧缓冲拷贝.md)、[`adr/0007`](adr/0007-一块全息屏只能接一台电脑.md)。

## 1. 传输层

- **载体**：CC `http.websocket`（`ws://` 内网调试 / `wss://` 公网）。**二进制**消息，不用 JSON。
- **方向**：服务器 → CC 是主流（帧）；CC → 服务器只有 ack / 统计。
- **单条消息 ≤ 48 KB**（给 128 KB 硬上限留一倍余量，也给 CC 侧留收包缓冲的余量）。
  一帧超过 48 KB 时拆成多条 `FRAME`（同 `seq`、不同 `part`），见 §5。
- **鉴权**：URL 带 `?token=<secret>`；服务器按 token 决定 room 与 region。

## 2. 消息类型

| 码 | 方向 | 名字 | 用途 |
|---|---|---|---|
| `0x01` | S→C | `HELLO` | 协商版本 / 块大小 / 区域 / 尺寸 / fps |
| `0x02` | C→S | `READY` | CC 报能力与自检结果 |
| `0x10` | S→C | `FRAME` | 帧数据（可能是某一 part） |
| `0x13` | C→S | `ACK` | 整帧收齐并画完 |
| `0x14` | S→C | `CONTROL` | play / pause / seek / fps / stop |
| `0x20` | C→S | `STATS` | 周期上报 |
| `0x30` | S→C | `PING` | 保活（防 CC 事件被吞后彻底静默） |
| `0x31` | C→S | `PONG` | 回 PING |

多字节整数 **大端**。有符号量（运动矢量）用 **`u8` + 偏移 128**（`实际值 = byte - 128`），
避开 Lua 的位运算与符号问题。

## 3. `HELLO`（0x01）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8 | `type` | `0x01` |
| 1 | u8 | `version` | 协议版本，当前 **1**；不匹配则 CC 拒绝并打印 |
| 2 | u8 | `block` | 块边长，**16**（默认）。必须是 2 的幂 |
| 3 | u8 | `fps` | 目标帧率 |
| 4 | u16 | `wall_w` | 整墙宽（如 640） |
| 6 | u16 | `wall_h` | 整墙高（如 360） |
| 8 | u16 | `region_x` | 本机负责区域左上角（**缓冲坐标**） |
| 10 | u16 | `region_y` | 同上 |
| 12 | u16 | `region_w` | 区域宽（第一版 = wall_w） |
| 14 | u16 | `region_h` | 区域高（第一版 = wall_h） |
| 16 | u8 | `flags` | 保留（第一版恒 0；多屏时 bit0 = 本机负责 sync） |
| 17 | u8 | `name_len` | room 名长度 |
| 18 | … | `name` | room 名（ASCII） |

CC 收到后：`resize(wall_w, wall_h)`、`setColorMapping(...)`、
`releaseAllFrameBuffer()` 后 `prevId = allocateFrameBuffer(region_w, region_h)`。

## 4. `FRAME`（0x10）

```
+0   u8   type      = 0x10
+1   u16  seq
+3   u8   flags     bit0 = KEY（本帧属于一次整帧重建）
+4   u8   part      当前分片序号，从 0 开始
+5   u8   parts     本帧总片数（1 表示不分片）
+6   u8   bx        ⌈region_w / block⌉
+7   u8   by        ⌈region_h / block⌉
+8   bitmap[⌈bx*by/8⌉]   行优先，1 = 本分片包含该块的数据
+…   按行优先顺序，依次处理每个 bit=1 的块：
       u8  mode
            1 = MV   （从 prev framebuffer 按整数位移拷贝）
            2 = RAW  （完整 block×block 像素）
       mode=1: i8 dx, i8 dy
       mode=2: block*block 字节像素（行优先，每像素 1 字节）
```

- `bit=0` 的块：**本分片不含该块**。若这是最后一帧的全部数据仍为 0，说明该块
  要么「不动」（显示缓冲保留上一帧内容），要么在**其它分片**里。
- `KEY` 帧：整个 `seq` 的所有块都是 `RAW`，等价于「整帧重建」。
  用于首帧、seek、场景切换、以及任何 prev 失效之后。
- bitmap 按**整个帧**的块网格计（每个分片各带一份，只置本片包含的位），
  方便解码器直接按同一张网格定位。

### 4.1 MV 的精确语义

设块在区域内的位置 `(px, py)`、边长 `B`。`prev` 是**上一帧整块区域**，
存在 `region_w × region_h` 的 hologram framebuffer 里。

**编码器的义务**：`(px+dx, py+dy)` 与 `(px+dx+B-1, py+dy+B-1)` 必须**都落在区域内**
（`0 ≤ … < region_w/h`），不允许越界。

**解码器的动作**：

```lua
h.blitFrameBufferArea(px, py, px + dx, py + dy, B, B, prevId)
```

坐标都是区域内的局部坐标（第一版 region 从 `0,0` 起，与缓冲坐标重合；
若将来 `region_x/y` 非 0，目标坐标要加上偏移）。

因为没有越界，`blitFrameBufferArea` 的 clamp 不会触发，语义就是纯粹的
「把上一帧的某个矩形搬到当前位置」。没有插值、没有边界延拓、没有残差。

> 解码器对越界 MV（不应出现）不做特殊处理：`blitFrameBufferArea` 会 clamp，
> 效果是不拷贝那部分。编码器建模时必须采用同一规则（`decode(encode(x)) == x` 的校验会抓住不一致）。

### 4.2 `RAW` 的像素编码

每像素 1 字节，`v` 解成四个 2-bit 通道：`R=(v>>6)&3, G=(v>>4)&3, B=(v>>2)&3, A=v&3`，
经 `setColorMapping(c0,c1,c2,c3)` 映射到 0–255。这与上一代 `player.lua` 的打包方式一致，
也是 hologram `blit` 直接吃的格式（`check8BitColor` 要求 0–255）。

## 5. 分片

一帧的数据量：
`header(8 + bitmap) + Σ(1 或 2 或 1+B² 字节)`。

640×360、16×16 块 ⇒ `bx=40, by=23`（`⌈360/16⌉=23`），`N=920` 块，bitmap **115 字节**。

| 场景 | 一帧字节 | 分片数（≤48 KB/片） |
|---|---|---|
| 静止（全跳过） | 8 + 115 = **123** | 1 |
| 典型（10% 像素 RAW） | ≈ 23 KB | 1 |
| 剧烈（50% RAW） | ≈ 116 KB | 3 |
| 全 RAW（KEY） | ≈ 231 KB | **5** |

分片规则：编码器按块顺序累加，达到 48 KB 就切下一片；**每片都带完整头部与 bitmap**。

> 为什么不用独立的 `CONT` 消息：`part`/`parts` 只是头部多两个字节，
> 却让「帧」和「消息」不再是同一个概念——解码器逻辑反而更简单（拼齐即得完整帧）。

## 6. 其它消息

### `ACK`（0x13，C→S）

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u8 | `type` = 0x13 |
| 1 | u16 | `seq` |
| 3 | u8 | `status`：0=ok，1=慢（超预算），2=错（附 `u8 errcode`） |
| 4 | u16 | `decode_ms`（可选，供服务器自适应降帧） |

Node 收到 `ok` 才发下一帧（**1 帧在飞**），这是唯一的流控。

### `CONTROL`（0x14，S→C）

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u8 | `type` = 0x14 |
| 1 | u8 | `cmd`：0=play，1=pause，2=seek，3=set_fps，4=stop |
| 2 | u32 | `arg`（seek=毫秒；set_fps=fps） |

### `STATS`（0x20，C→S）

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u8 | `type` = 0x20 |
| 1 | u16 | 最近 1 s 的帧数 |
| 3 | u16 | 平均 `decode_ms` |
| 5 | u16 | 累计丢帧 |
| 7 | u8 | 状态位（调试用） |

### `PING`/`PONG`（0x30/0x31）

`PING` 每 200 ms 一次，内容空；CC 必须回 `PONG`。
**为什么需要**：CC 调用 hologram 的主线程 API 时会吞掉排队事件（上一代实测），
一个纯 timer 驱动的循环可能「静默」。周期消息是让事件循环持续转动的可靠手段。

## 7. 容器格式 `.ccv`（离线文件）

```
0   4B  magic "CCV1"
4   u8  version (1)
5   u8  block   (16)
6   u8  fps
7   u8  reserved
8   u16 wall_w
10  u16 wall_h
12  u16 region_x
14  u16 region_y
16  u16 region_w
18  u16 region_h
20  u32 frame_count
24  u32 index_offset
28  u32 duration_ms
32  …   预留到 48
--
file[index_offset] = frame_count 条索引：
    u32 offset        该帧第一个分片的文件偏移
    u16 length        该帧所有分片的字节数之和
    u16 parts         分片数
    u32 time_ms       该帧的呈现时间戳
--
每个 frame 的数据 = §4 的若干条 FRAME 消息体（**不含** type 字节）
```

第一版一个视频一个目录：

```
videos/<片名>/
├── meta.json       标题、时长、尺寸、fps、块大小
└── video.ccv       单文件（region = 整墙）
```

将来上多块屏时按屏拆成 `screen0.ccv`、`screen1.ccv`…（MV 不能跨屏）。

## 8. 版本与兼容

- `version` 只在不兼容时 +1；CC 遇到未知版本**拒绝并打印**，不要「尽力解析」。
- `block` 是运行期参数（`HELLO.block`）：改成 32×32 **不需要**升版本，
  但**编码器与 CC 必须一致**，所以由服务器下发。
- 新增 `mode`（例如 3 = 8×8 子块 MV）属于不兼容扩展 ⇒ 升 `version`。
  CC 遇到未知 `mode` 必须报错退出（不能静默画错）。

## 9. 一个完整的例子

640×360、16×16 块 ⇒ `bx=40, by=23`，920 块，bitmap 115 字节。
第 7 帧只有块 0（RAW）与块 1（MV，右移 2 px）有数据：

```
10 0007 00 00 01 28 17 [03 00 00 …112 字节]   ← FRAME seq=7 flags=0 part=0/1 bx=40 by=23
02 [256 字节]                                  ← 块0: RAW
01 82 00                                       ← 块1: MV dx=+2 dy=0
```

静止画面的情形：920 个 bit 全 0，消息只有 8 + 115 = **123 字节/帧**（≈ 2.4 KB/s，20 fps）。
