# 01 · 码流格式（ccv v1）

> 2026-11-15 修订：块大小改为 **16×16**，MV 语义改为「从上一帧**帧缓冲**取」，
> 依据见 [`adr/0006`](adr/0006-MV用帧缓冲拷贝.md)。

## 1. 传输层

- **载体**：CC `http.websocket`（`ws://` 内网调试 / `wss://` 公网）。**二进制**消息，不用文本/JSON。
- **方向**：服务器 → CC 是主流（帧 + 控制）；CC → 服务器只有 ack / 上报。
- **单消息上限**：
  - CC 侧硬上限 `max_websocket_message = 131072` 字节（`config/computercraft-server.toml` 的 `*` 规则）→ 按 **< 64 KB** 设计。
  - 320×180 区域、16×16 块（240 块）最坏情况：
    - 全 RAW：57600 字节像素 + 240 字节模式 + 30 字节 bitmap ≈ **57.9 KB** ✅
    - 每块都带 MV 参数：多 480 字节 ✅
  - 仍留 `0x11 CONT` 分片机制，供将来更大的区域使用。
- **鉴权**：URL 带 `?token=<room_secret>`；服务器按 token 决定 room 与 region。

## 2. 消息类型总表

| 码 | 方向 | 名字 | 用途 |
|---|---|---|---|
| `0x01` | S→C | `HELLO` | 协商版本 / 块大小 / 分区 / 尺寸 / fps |
| `0x02` | C→S | `READY` | CC 报能力与自检结果 |
| `0x10` | S→C | `FRAME` | 一帧的块数据 |
| `0x11` | S→C | `CONT` | 大帧的后续分片（>64 KB 时才用） |
| `0x13` | C→S | `ACK` | 某帧已画完（含耗时） |
| `0x14` | S→C | `CONTROL` | play / pause / seek / fps / stop |
| `0x20` | C→S | `STATS` | 周期上报：帧率、解码耗时、丢帧 |
| `0x30` | S→C | `PING` | 保活（防 CC 事件被吞后彻底静默） |
| `0x31` | C→S | `PONG` | 回 PING |

多字节整数 **大端**。有符号量（运动矢量）用 **`u8` + 偏移 128**
（`实际值 = byte - 128`），避免 Lua 的位运算与符号问题。

## 3. `HELLO`（0x01）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8 | `type` | `0x01` |
| 1 | u8 | `version` | 协议版本，当前 **1**；不匹配则 CC 拒绝并打印 |
| 2 | u8 | `block` | 块边长，**16**（默认）。必须是 2 的幂 |
| 3 | u8 | `fps` | 目标帧率 |
| 4 | u16 | `wall_w` | 整墙宽（如 640） |
| 6 | u16 | `wall_h` | 整墙高（如 360） |
| 8 | u16 | `region_x` | 本机负责区域左上角（**全局缓冲坐标**） |
| 10 | u16 | `region_y` | 同上 |
| 12 | u16 | `region_w` | 区域宽（如 320） |
| 14 | u16 | `region_h` | 区域高（如 180） |
| 16 | u8 | `flags` | bit0 = 本机是 master（负责 `sync`） |
| 17 | u8 | `name_len` | room 名长度 |
| 18 | … | `name` | room 名（ASCII） |

CC 收到后：`resize(wall_w, wall_h)`、`setColorMapping(...)`、分配 prev framebuffer、
记下 `region_*` 与 `block`。

## 4. `FRAME`（0x10）

```
+0   u8   type      = 0x10
+1   u16  seq
+3   u8   flags     bit0 = KEY   本帧不依赖上一帧（prev 会被覆盖成整帧）
+5   u8   bx        ⌈region_w / block⌉
+6   u8   by        ⌈region_h / block⌉
+7   bitmap[⌈bx*by/8⌉]   行优先，1 = 有数据
+…   按行优先顺序，依次处理每个 bit=1 的块：
       u8  mode
            1 = MV   （从 prev framebuffer 按整数位移拷贝）
            2 = RAW  （完整 block×block 像素）
       mode=1: i8 dx, i8 dy
       mode=2: block*block 字节像素（行优先，每像素 1 字节）
```

- `bit=0` 的块：**不动**。显示缓冲里它保持上一帧的内容（上一帧已经画在那里），
  而 prev framebuffer 里也是同样的内容 ⇒ 天然一致。
- `KEY` 帧：prev 内容无意义，所有有数据的块必须是 `RAW`；等价于「整帧重建」。
- 若 `bx*by` 不是 8 的倍数，bitmap 补零到整字节。

### 4.1 MV 的精确语义

设块在区域内的位置 `(px, py)`、边长 `B`。`prev` 是**上一帧整块区域**，
存在一个 `region_w × region_h` 的 hologram framebuffer 里（见 `docs/03`）。

**编码器的义务**：`(px+dx, py+dy)` 与 `(px+dx+B-1, py+dy+B-1)` 必须**都落在区域内**
（`0 ≤ … < region_w/h`）。即 MV 的源矩形完全在区域内，**不允许越界**。

**解码器的动作**：

```lua
h.blitFrameBufferArea(
    region_x + px, region_y + py,   -- 目标（全局缓冲坐标）
    px + dx,       py + dy,         -- 源（prev 内的局部坐标）
    B, B,
    prevId)
```

因为编码器保证了不越界，`blitFrameBufferArea` 的 clamp 不会触发，语义就是纯粹的
「把上一帧的某个矩形搬到当前位置」。没有插值、没有边界延拓、没有残差。

> 解码器对越界的 MV（不应出现）不做特殊处理：`blitFrameBufferArea` 会 clamp，
> 效果是不拷贝那部分。编码器建模时必须采用同一规则（`decode(encode(x)) == x` 的校验会抓住不一致）。

### 4.2 `RAW` 的像素编码

每像素 1 字节，`v` 解成四个 2-bit 通道：`R=(v>>6)&3, G=(v>>4)&3, B=(v>>2)&3, A=v&3`，
经 `setColorMapping(c0,c1,c2,c3)` 映射到 0–255。这与上一代 `player.lua` 的打包方式一致，
也是 hologram `blit` 直接吃的格式（`check8BitColor` 要求 0–255）。

## 5. 其它消息

### `ACK`（0x13，C→S）

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u8 | `type` = 0x13 |
| 1 | u16 | `seq` |
| 3 | u8 | `status`：0=ok，1=慢（超预算），2=错（附 `u8 errcode`） |
| 4 | u16 | `decode_ms`（可选，供服务器自适应降帧） |

### `CONTROL`（0x14，S→C）

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u8 | `type` = 0x14 |
| 1 | u8 | `cmd`：0=play，1=pause，2=seek，3=set_fps，4=stop |
| 2 | u32 | `arg`（seek=毫秒；set_fps=fps） |

### `STATS`（0x20，C→S）

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u8 | `type` = 0x20 |
| 1 | u16 | 最近 1 s 的帧数 |
| 3 | u16 | 平均 `decode_ms` |
| 5 | u16 | 累计丢帧 |
| 7 | u8 | 状态位（调试用） |

### `PING`/`PONG`（0x30/0x31）

`PING` 每 200 ms 一次，内容空；CC 必须回 `PONG`。
**为什么需要**：CC 调用 hologram 的主线程 API 时会吞掉排队事件（上一代实测），
一个纯 timer 驱动的循环可能「静默」。周期消息是让事件循环持续转动的可靠手段。

## 6. 分片（`CONT`，0x11）

仅当单帧 > 64 KB 时使用（例如将来单机负责更大区域）。

```
+0 u8  type = 0x11
+1 u16 seq
+3 u8  part     从 0 开始
+4 u8  parts    总数
+5 …   紧接 FRAME 消息去掉首字节后的对应切片
```

## 7. 容器格式 `.ccv`（离线文件）

```
0   4B  magic "CCV1"
4   u8  version (1)
5   u8  block   (16)
6   u8  fps
7   u8  reserved
8   u16 wall_w
10  u16 wall_h
12  u16 region_x
14  u16 region_y
16  u16 region_w
18  u16 region_h
20  u32 frame_count
24  u32 index_offset
28  u32 duration_ms
32  …   预留到 48
--
file[index_offset] = frame_count 条索引：
    u32 offset
    u16 length
    u16 seq
--
每个 frame 的数据 = §4 的 FRAME 消息体（**不含** type 字节）
```

**一个 quadrant 一个 `.ccv`**（MV 不能跨区域），统一放在一个目录：

```
videos/<片名>/
├── meta.json
├── q0-0.ccv     region 0,0
├── q0-1.ccv     region 320,0
├── q1-0.ccv     region 0,180
└── q1-1.ccv     region 320,180
```

## 8. 版本与兼容

- `version` 只在不兼容时 +1；CC 遇到未知版本**拒绝并打印**，不要「尽力解析」。
- `block` 是运行期参数（不是版本号的一部分）：改成 32×32 不需要升版本，
  但**编码器与 CC 必须一致**，所以由 `HELLO.block` 下发。
- 新增 `mode`（例如 3 = 8×8 子块 MV）属于不兼容扩展 ⇒ 升 `version`。
  CC 遇到未知 `mode` 必须报错退出（不能静默画错）。

## 9. 一个完整的例子

320×180 区域、16×16 块 ⇒ `bx=20, by=12`，240 块，bitmap 30 字节。
第 7 帧只有块 0（RAW）与块 1（MV，右移 2 px）有数据：

```
10 00 07 00 14 0C [03 00 00 …29 字节]   ← FRAME seq=7 flags=0 bx=20 by=12 bitmap
02 [256 字节]                            ← 块0: RAW
01 82 00                                 ← 块1: MV dx=+2 dy=0
```

静止画面的 `DUP` 情形：256 个 bit 全 0，消息只有 7+30 = **37 字节/帧**（≈ 0.7 KB/s）。
