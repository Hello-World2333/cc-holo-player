# ADR-0006 · 运动补偿用 `blitFrameBufferArea`，不用 Lua 表

- 状态：**已接受**（推翻 ADR-0003 的一部分与 `docs/02` §4 的成本模型）
- 日期：2026-11-15
- 相关：[0003](0003-自定义块级码流.md)、[`../02-解码预算与编解码器.md`](../02-解码预算与编解码器.md)

## 背景

ADR-0003 假设「MV = 64 次 `string.sub` + 一次 4096 元素的表 + blit」，成本与 RAW 相同（约 1.3 ms/块）。
这个假设是**反编译 `void_power-1.0.7.fix2.jar` 之后被推翻的**，不需要真机探针。

## 反编译事实

### 1. `blit` 只接受 Lua 表，且每像素两次哈希查找

`P_HologramPeripheral.blit(IArguments)` 的关键字节码：

```
107: getTable(4)                      → java.util.Map     ← 只接受表，不接受字符串
195: i13 = (i16 + i19 - i2)                               ← 像素线性索引（0 起）
204: map.containsKey(Double.valueOf(i13))                  ← ① Double 装箱 + 哈希查找
222: ((Double) map.get(Double.valueOf(i13))).longValue()  ← ② 再来一次
244: CCUtils.check8BitColor(int)                           ← 每次范围检查
```

⇒ 每个像素 **2 次 `Double.valueOf` 分配 + 2 次 `HashMap` 查找**，外加 CC 把整个 Lua 表
marshalling 成 `Map` 的一次性 O(n) 拷贝。这就是实测 0.14 µs/px 的来源，**Lua 侧无法规避**。

**结论：`blit` 是否接受字符串——不接受。但也不再关心了。**

### 2. `blitFrameBufferArea` 是纯 Java 逐字节拷贝

`@LuaFunction public void blitFrameBufferArea(IArguments)`，与 wiki 文档完全一致：

```
blitFrameBufferArea(ax, ay, bx, by, bw, bh, bufferId [, mode])
   ax, ay      目标左上（当前激活缓冲）
   bx, by, bw, bh  源裁剪矩形
   bufferId    源缓冲区 id（**-1 = 显示缓冲**）
   mode        0 = 完全覆盖（默认）  1 = 只复制 (pixel & 3) != 0 的像素
```

内层循环（字节码 289–298）：

```
aload 16   ; dst.canva_buf
iload 24 / 25   ; dst 行偏移 + 列
aload 17   ; src.canva_buf
iload 19        ; src 行偏移 + 列
baload → bastore
```

**没有任何装箱、没有哈希、没有 Lua 表。** 4096 个像素 ≈ 微秒级。

### 3. `getBuffer(-1)` / `activateFrameBuffer(-1)` = 显示缓冲

```
HoloFrameBufferManager.getBuffer(int i):
    if (i < 0) return te.buffer;          // ← 显示缓冲
activate(int i):
    if (i < 0) { currentActivated = te.buffer; return; }
```

⇒ 可以「从显示缓冲读、往自有 framebuffer 写」，反之亦然。唯一的限制是
`blitFrameBufferArea` 开头有 `if (src == getCurrentActivated()) return;`——不能自己拷自己。

### 4. Framebuffer 容量与限制

| 项 | 值 | 出处 |
|---|---|---|
| framebuffer 数量 | **16** 个（id 0..15） | `P_HologramPeripheral` 构造器 `bipush 16` |
| 每个的尺寸上限 | `w*h ≤ 393216` | `HoloFrameBufferManager.allocate` / `HoloFrameBuffer.resize` |
| 像素字节范围 | 0–255（`8 bit color need in rage of [0, 255]`） | `CCUtils.check8BitColor` |
| `resize` 语义 | **重新 `new byte[w*h]`**（内容丢失），可选填 109 | `HoloFrameBuffer.resize` |
| `sync` 代价 | `arraycopy(w*h)` + **zlib Deflater 压缩整个缓冲** | `HologramTE.fillSendBufferAndMarkDirty` + `HoloSyncData.compress` |

## 决策

**MV 不再由 Lua 计算，改为一条 Java 调用：**

```lua
-- 每台电脑分配一个「上一帧」缓冲区（自己 region 大小，如 320×180）
local prevId = h.allocateFrameBuffer(320, 180)

-- 每帧：
h.activateFrameBuffer(-1)                        -- 目标 = 显示缓冲
for 每个数据块 do
    if mode == RAW then
        h.blit(x, y, bw, bh, buildTable(pixels))  -- 唯一需要 Lua 表的地方
    elseif mode == MV then
        h.blitFrameBufferArea(x, y, x + dx, y + dy, bw, bh, prevId)   -- Java memcpy
    end
end
-- 帧末：把本区域从显示缓冲存进 prev（一条 Java 调用）
h.activateFrameBuffer(prevId)
h.blitFrameBufferArea(0, 0, regionX, regionY, regionW, regionH, -1)
h.activateFrameBuffer(-1)
```

## 成本模型的变化

| 操作 | ADR-0003 的假设 | 实测/反编译后的实际 |
|---|---|---|
| SKIP | ~0 | ~0（不变） |
| **MV（64×64）** | **1.3 ms** | **~5–15 µs（约 100 倍便宜）** |
| MV（16×16） | 不可行（块太多） | ~5 µs/块 |
| RAW（64×64） | 1.3 ms | 1.3 ms（不变，4096 px × 0.31 µs） |
| RAW（16×16） | — | 0.08 ms（256 px × 0.31 µs） |

**关键后果：解码成本 ∝ 每帧「新露出」的像素数，与运动量无关。**

这正是真正视频编码器想要的形状——平移镜头（MV 覆盖绝大部分）几乎免费，
只有遮挡/新内容（RAW）才花钱。而在 ADR-0003 的假设下，平移镜头同样昂贵，
编解码器的设计空间被严重压缩。

## 后果

**好**

- **可以上细粒度 MV**（16×16 甚至 8×8），画质接近 MPEG-1，而成本只跟 RAW 像素挂钩。
- **CC 端解码器大幅简化**：不再需要 Lua 侧的 `prev` 字符串、不需要按行/整串拼接 `cur`。
  `docs/03` 的 §3（`cur` 怎么拼得动）整节作废。
- **单机可负责更大区域**：按 320×180 每帧约 3–7 ms 估算，640×360 也在预算内 ⇒ 多屏拼接可以少用电脑。
- `docs/06` 的 §1（探测 blit 是否吃字符串）与 §3（整串 vs 按行表）**两个待测项直接消失**。

**坏 / 代价**

- 依赖 VoidPower 的**帧缓冲 API 语义**（`getBuffer(-1)`、`activate(-1)`、mode 值）。
  这是文档化的公开 API（wiki 有 `blitFrameBufferArea` 一节），但**版本相关**：升级 mod 要复测。
- framebuffer 存在**方块实体**里，电脑重启不释放（上一代踩过：`releaseAllFrameBuffer` 是必需的）。
  每台电脑启动时先 `releaseAllFrameBuffer()` 再分配自己的 prev。
- 多台电脑共享同一块 hologram 的 16 个 framebuffer 槽位 ⇒ 4 台各占 1 个，仍有 12 个余量；
  但每台都要**只申请自己的**，不能互相 release（`releaseAllFrameBuffer` 会清掉别人的）。
  ⚠️ 这一点必须让「每台电脑有自己的 hologram 外设对象」成立——若 4 台是通过 CEE 数据网络
  访问**同一台** hologram 的**同一个** peripheral 实例，则 `releaseAllFrameBuffer` 会互相清空。
  见「未解」。
- `sync()` 的 zlib 压缩是**整块缓冲**（230400 B），无法只压变化区域 ⇒ 每帧固定 1–2 ms 服务端 CPU。

## 未解（必须在实现前确认）

| 问题 | 影响 | 怎么确认 |
|---|---|---|
| 4 台电脑是否共享**同一个** `P_HologramPeripheral` 实例 | 决定 `releaseAllFrameBuffer` 是否安全、framebuffer id 是否互相可见 | 在 4 台上各 `h.getAllocatedFrameBuffers()`，看是否看到"别人的" id |
| 每台电脑的 `activateFrameBuffer` 是否互相干扰 | 若共享实例，`currentActivated` 是**一个**字段 ⇒ 4 台会互相切缓冲，**灾难** | 同上，且观察两台同时画是否串台 |

> 这两条是**真正的阻塞项**，而且只能用真机确认（纯读 jar 无法知道运行时是 1 个实例还是 4 个）。
> 若确认共享，退路是：**单机负责整个 640×360**（按本 ADR 的成本估算完全可行），
> 或者每台配**独立的一块 hologram**（用多块屏拼出更大的墙，跨屏用另一层同步）。
