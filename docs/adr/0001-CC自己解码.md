# ADR-0001 · 解码放在 CC，而不是 MC 本机代理

- 状态：**已接受**
- 日期：2026-11-15
- 相关：[0002](0002-不用纯Lua-VP8.md)、[0004](0004-fabric只跑控制.md)

## 背景

视频要在游戏里播放，`hologram.blit` 需要的是**每像素 1 字节的原始数据**（`RRGGBBAA` 各 2 bit）。
压缩视频必须先解码。可选的落点有三个：

| 方案 | 解码在哪 | MC 机器要装什么 | 公网流量（640×360@20） |
|---|---|---|---|
| A | 公网 Node | 无 | **37 Mbps 持续**（raw 直发） |
| B | MC 本机代理进程 | **node + ffmpeg** | 1–3 Mbps |
| C | **CC 自己** | **无** | 1–6 Mbps |

上一代（`~/cc-holo-player`）用的是 B：宿主上跑 `node dist/server.js`（含 ffmpeg 实时转码），
CC 通过 `ws://127.0.0.1:18755` 取 raw 瓦片。

## 决策

采用 **C**：**Node 只负责把视频变成压缩码流，解码由 CC 的 Lua 完成。**

## 理由

1. **MC 机器零新依赖**是该项目的硬要求（用户明确提出：Node 在公网、MC 在另一台机器）。
   方案 B 要求 MC 宿主上有一个常驻 Node 进程 + ffmpeg，部署/升级/排障都会落到「那台机器」。
2. **公网带宽**：方案 A 的 37 Mbps 持续上行在 VPS 上是不可接受的（计入出口流量），
   方案 C 的 1–6 Mbps 才现实。
3. **可移植**：CC 端只有 Lua + ws，换服务器、换存档、给朋友复制都不用改宿主机。
4. 性能上**可行**，但前提是码流为 Lua 定制（见 ADR-0002/0003），不能沿用标准编码器。

## 后果

**好**

- MC 服务器保持「一个普通 MC 服务器」的形态。
- 码流可以按 CC 的能力裁剪（这是 ADR-0003 的来源）。
- 天然支持公网 + 无入站端口（CC 主动外连）。

**坏 / 代价**

- 必须**自己设计并实现编解码器**，还要位精确校验（没有现成库）。
- CC 的算力成了硬上限，画质/分辨率/帧率都被它压住。
- 调试链路长：源视频 → 码流 → CC 解码 → 屏幕，任一环坏都要能单独复现 ⇒ `tools/` 必须具备离线校验能力。

## 被否决的方案

- **A（raw 直发）**：37 Mbps 且无压缩，CC 侧仍要转表，只省了「解码」这一小步，带宽代价过大。
- **B（本机代理解码）**：违背「MC 机器零依赖」；且与上一代重复。
- **在 mod 里写原生解码器**（Java 侧解 VP8，Lua 只拿像素）：性能最好，但需要改 mod / 装新 jar，
  目标是「不新增依赖」，且要维护 Java。**未来若成为瓶颈可重新评估**，届时码流格式可以保持不变。

## 证据

- `docs/02` §2：CC 每帧预算 50 ms，其中留给解码的余量 20–30 ms。
- 服务器配置：`config/computercraft-server.toml` 中 `http.rules` 的 `host="*"` → `action="allow"`，
  `max_websocket_message = 131072` ⇒ CC 可以主动连任意公网域名，单消息上限 128 KB。
- 上一代的 raw 通路实测：320×180 一帧「转表 + blit」= 18 ms（`computer/75/probe3.log`），
  证明 CC 侧**即便不解码**也已经吃掉可观预算——这是「必须让码流为 Lua 定制」的直接原因。
