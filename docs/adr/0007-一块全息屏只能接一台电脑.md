# ADR-0007 · 一块 hologram 只能接一台电脑（共享外设实例）

- 状态：**已接受（推翻 `docs/04` 的「4 台共享一块缓冲」前提）**
- 日期：2026-11-15
- 相关：[0006](0006-MV用帧缓冲拷贝.md)、[`../04-多屏拼接与同步.md`](../04-多屏拼接与同步.md)

## 背景

`docs/04` 的第一版设计沿用上一代：4 台电脑各写一块 `region`，但**写的是同一张 640×360 缓冲**。
`docs/06` §1 把它列为「唯一的阻塞项」，以为只能用真机确认。

**不需要真机——jar 里写得很清楚。**

## 反编译事实

### 1. 一个 hologram 方块只有**一个**外设实例

```java
// HologramTE
private P_HologramPeripheral peripheral;

public P_HologramPeripheral getPeripheral() {
    if (peripheral == null)
        peripheral = new P_HologramPeripheral(this);   // 懒加载，缓存进字段
    return peripheral;
}
```

⇒ 无论多少台电脑访问同一个 hologram 方块，拿到的都是**同一个对象**。

### 2. 多台电脑共享访问是**被支持**的，但共享全部状态

```java
public void attach(IComputerAccess computer) { computers.add(computer); }
public void detach(IComputerAccess computer) { computers.remove(computer); }
```

`computers` 是个 `Set`，说明作者预期「多台电脑接同一个 hologram」。
但 `P_HologramPeripheral` 内部**没有任何 per-computer 状态**——`IComputerAccess` 只用于 `pushEvent`。

于是下面这些全是**跨电脑共享**的：

| 状态 | 位置 | 共享的含义 |
|---|---|---|
| `currentActivated` | `HoloFrameBufferManager` 的**单个字段** | 「当前激活缓冲」是全局唯一的 |
| `buffers[16]` | 同上 | 16 个 framebuffer 槽位全墙共用 |
| `releaseAllFrameBuffer()` | 清的正是 `buffers[]` | A 机调用会**清掉 B 机的 prev** |
| `te.buffer`（显示缓冲） | TE | 设计如此，本来就是共享的 |

### 3. 致命点：`activateFrameBuffer` 是全局游标

```java
public void activate(int i) {
    if (i < 0) { currentActivated = te.buffer; return; }   // ← 单个字段
    ...
    currentActivated = buffers[i];
}
```

而 `blit` / `blitFrameBufferArea` 的目标都是 `getCurrFB()` = `currentActivated`。

⇒ **A 机执行 `activateFrameBuffer(-1)` 之后，B 机下一次 `blit` 的目标就变了。**
这不是理论风险：`activate` 的字节码只是给一个字段赋值。

## 结论

**「4 台电脑共享一块 hologram 缓冲、各写自己区域」——不可行。**
上一代之所以能跑，是因为 4 台只做 `blit`（目标恒为显示缓冲），
且从不 `allocateFrameBuffer` / `activateFrameBuffer`。

一旦要用 ADR-0006 的 Java 侧 MV（必须 `activate` 到 prev 缓冲），共享就必然打架。

## 三条可行路线

| | 形态 | 每帧成本（640×360） | 复杂度 | 何时该选 |
|---|---|---|---|---|
| **A** | **1 块 hologram + 1 台电脑** | 典型 ≈12 ms；全 RAW ≈74 ms | ⭐ 最低 | 推荐作为第一版 |
| **H** | 1 块 hologram + 4 台，**只有 master 做 MV** | master ≈5 ms；渲染机 ≈2 ms | ⭐⭐⭐⭐ 最高 | 想保留 4 机分工 |
| **B** | **N 块 hologram + N 台**（每块一台） | 每台 ≈1–3 ms | ⭐⭐ | 需要 > 640×360 时**只能**这样 |

### A. 单机（推荐）

一块 640×360 hologram，一台电脑全包。**根本不存在共享问题。**

- 32×32 块 ⇒ 240 块：MV 调用 ≈2.4 ms，典型 10% RAW ≈7.1 ms，display→prev 拷贝 ≈0.1 ms，
  再加 master 自己的 `sync`（zlib 压 230400 B）≈1–2 ms ⇒ **合计约 11–12 ms**，20 fps 有余。
- 代价：**全 RAW（场景切换）≈74 ms**，会掉到 13 fps。
  缓解办法是「渐进刷新」：把关键帧拆成 3 帧，每帧只 RAW 三分之一，其余跳过 ⇒ 每帧 ≈26 ms，不掉帧。
- 为什么上一代要 4 台？因为那时传的是 **raw 全帧**（230400 px 必须全量 blit = 71 ms）。
  现在 MV 免费，**4 台的主要理由消失了**。

### H. 4 台共享一块，master 独做 MV

渲染机只负责把 **RAW 块** `blit` 进显示缓冲（此时 `currentActivated` 恰好是显示缓冲）；
master 承担**全墙**的 MV（`blitFrameBufferArea`，从自己的 prev 读）；
全部 ack 齐之后，master 短暂 `activate(prevId)` → 把显示缓冲整块拷进 prev → `activate(-1)` → `sync()`。

安全的前提是 **ack 栅栏**：渲染机 ack 之后到下一帧之前不碰外设，所以 master 的 activate 窗口是独占的。
额外好处：**MV 可以跨 quadrant**，压缩率比分区独立更好。

代价：master 要额外收发 MV 向量；Node 要按「块」而不是「区域」分派；出错时的竞态极难复现。

### B. 每块 hologram 接一台电脑

每台电脑有自己的 hologram 方块 ⇒ 自己的 `P_HologramPeripheral` ⇒ 自己的 `currentActivated`，
**共享问题彻底消失**，而且这是唯一能突破 393216 像素上限的路线。

- 拼接靠 `setOffset` / `setRotation` / `setScale`（三者都是公开的 `@LuaFunction`），
  **可以在 Lua 里程序化对齐**，不必手工摆。
- 代价：跨屏撕裂要新的同步层（`docs/04` §5）；多一个方块、多一台电脑；
  接缝处的像素对齐需要实测（`screenScale` 是 float，可能有亚像素误差）。

## 决策

**第一版走 A**：一块 640×360 hologram，一台电脑，32×32 块。

理由：

1. 它把「共享外设实例」这个整个架构里最不可控的风险**变成不存在**。
2. 成本按实测常量算得过来（11–12 ms / 预算 50 ms），且还有渐进刷新兜底。
3. 代码量最小：没有 fabric 栅栏、没有 ack 屏障、没有跨机竞态，一个进程就能调试。
4. 用户的原始诉求是「**多屏拼接以支持更高分辨率**」。640×360 只需要一块屏，
   真正需要拼接是在 **> 393216 像素**时——那时走 B（每块屏一台电脑），本 ADR 已经给出路线。

**保留**：`docs/01` 的码流格式**不需要改**——它本来就是「一个 region 一条流」，
单机时 region = 整墙（`region_x=0, region_y=0, region_w=640, region_h=360`）。
以后要上 B，只是把它拆成 N 条流。

## 后果

**好**

- 删掉 `docs/04` §3 的整节（fabric ack 栅栏、master 选举、丢帧仲裁）——第一版**不需要**。
- `docs/03` 的「共享实例风险」一节作废。
- 调试面从「4 台 + 1 条 fabric + 1 个 Node」降到「1 台 + 1 个 Node」。

**坏 / 代价**

- 单机是**单点**：它卡住整墙就卡住。
- 全 RAW 帧 74 ms 需要「渐进刷新」这个额外机制（但比 ack 栅栏简单得多）。
- 用户如果坚持「4 台电脑各干一块」的画面上呈现，这条路不满足——需要 H 或 B。
