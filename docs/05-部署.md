# 05 · 部署与运维

## 1. 拓扑

```
公网 VPS（有公网 IP / 域名 + TLS）
  ├─ caddy / nginx  →  wss://wall.example.com/play
  ├─ node 进程      →  码流分发（+ 可选实时转码）
  └─ 磁盘           →  /srv/wall/videos/<片名>/{q0-0.ccv,q0-1.ccv,q1-0.ccv,q1-1.ccv,meta.json}

你家 / 机房
  └─ MC 服务器（**不需要端口映射、不需要公网 IP**）
       └─ CC 电脑们 → 主动外连 wss
```

**关键：连接方向是 CC 主动外连。** MC 服务器不需要任何入站端口、不需要 DDNS，
这会省掉一大半部署麻烦（上一代因为代理在宿主机上，也不需要；这一代同样保持）。

## 2. 公网侧

### 2.1 依赖

| 组件 | 什么时候需要 |
|---|---|
| Node（建议 20+） | 总是（码流分发） |
| ffmpeg（要带 libvpx / libx264） | **仅转码时**；只播已经转好的 `.ccv` 不需要 |
| caddy 或 nginx | 提供 TLS（`wss://`） |

> 因为「第一版只播一个码流」，最省事的部署是：本地转好 `.ccv` 丢上去，VPS 只跑一个静态+ws 分发进程。

### 2.2 反向代理要点

```
# caddy
wall.example.com {
    reverse_proxy /play* 127.0.0.1:18755
}
```

- **必须关掉代理的响应缓冲**（nginx: `proxy_buffering off;`），否则帧会被攒着发。
- 超时放宽（`proxy_read_timeout 3600s`），否则空闲时连接被掐。
- 不需要 `X-Forwarded-For` 之类的逻辑，但建议记录客户端 IP 用于排障。

### 2.3 带宽

| 墙 | 典型码率 | 月度流量（按每天 4 h） |
|---|---|---|
| 2×2，P1 典型内容 | 3–8 Mbps | ≈ 0.5–1.2 TB |
| 2×2，P2 典型内容 | 2–6 Mbps | ≈ 0.4–0.9 TB |

VPS 的**出口流量计费**通常是这类项目的真正成本项，比 CPU 重要。

## 3. CC 侧

### 3.1 服务器配置检查表

`config/computercraft-server.toml`：

| 项 | 需要 | 本服当前 |
|---|---|---|
| `http.enabled` | true | ✅ |
| `http.websocket_enabled` | true | ✅ |
| `http.max_websockets` | ≥ 每台 1 | 2048 ✅ |
| `http.rules` 放行目标域名 | 需要 | `host="*" allow` ✅ |
| `max_websocket_message` | ≥ 64 KB | 131072 ✅ |
| `http.bandwidth.global_download` | 够 4 台合计 | 32 MB/s ✅ |

> 如果将来把 `*` 规则收紧成白名单，记得把公网域名加进 `host`，否则 CC 连不上。

### 3.2 CC 电脑准备

```lua
-- /wall.cfg（textutils.serialise 格式，**不带 return**）
{ url = "wss://wall.example.com/play?token=SECRET",
  name = "wall1",
  log = true }
```

```lua
-- /startup.lua
shell.run("/wall.lua")
```

- 每台电脑：CEE 数据网络要能看到 **hologram**（`peripheral.find("hologram")` 或 `cee.getPeripherals(pin)`）。
  注意本服 `adjacentLinking = false`：贴着放不算连上，必须接 **Peripheral Cable**。
- 电子盘默认 1 MB，脚本 + 日志绰绰有余（**不要**往电脑上放视频文件）。
- 换脚本后必须重启电脑（CC 只在开机读 `startup.lua`）：`computercraft shutdown/turn-on`，或游戏内 `Ctrl+R`。

### 3.3 时钟/延迟

- CC 的 `os.epoch("utc")` 与服务器时间对齐，可用于统计延迟，但**不要用它做帧节奏**（会被事件吞影响）。
- 公网 RTT 建议 < 150 ms；> 300 ms 时 20 fps 的锁步会明显变迟钝（可降到 10–15 fps）。

## 4. 转码流程（离线，第一版推荐）

```
1. 准备源视频（任意 mp4/mkv，ffmpeg 能解的）
2. 转码：  node dist/transcode --in movie.mp4 --out /srv/wall/videos/movie --wall 640x360 --fps 20 --profile 1
3. 产物：  movie/meta.json + movie/q0-0.ccv … q1-1.ccv
4. 校验：  node dist/verify --in movie        # 逐帧 encode→decode→对比，必须 0 差异
5. 上传：  rsync 到 VPS
6. 播放：  node dist/serve --dir /srv/wall/videos --port 18755
```

`verify` 是**强制步骤**：码流是自定义的，没有「播放器能放就算对」这回事。

## 5. 排障

| 现象 | 先查 |
|---|---|
| CC 连不上 | `http.checkURL("https://…/health")`；`http.rules` 是否放行；TLS 证书是否有效（CC 用 Java 的信任库，自签证书会失败） |
| 连上但黑屏 | `HELLO` 版本是否匹配；`region` 是否为 0；是否有人 `sync` |
| 画面撕裂（半屏新半屏旧） | 有第二台在调 `sync()`；或 master 的 ack 没齐就 sync |
| 只有一块象限动 | 那台的码流断了 / 那台 `blit` 报错（看日志） |
| 越来越慢 | 每帧临时表没释放 → GC 压力；对照 `docs/02` 的预算表看哪个瓦片成了 `RAW` |
| 全墙卡 1 s 然后跳变 | 锁步被慢机拖累；看 `STATS` 的 `decode_ms` |
| 电脑重启后花屏 | 缓冲里残留旧像素；重连时应等一个 `KEY` 帧再画 |

## 6. 运维

- **日志**：CC 端别写太多（电子盘小）；Node 端保留每 room 的帧率/码率曲线。
- **监控**：`GET /health` 返回 `{ok, rooms, clients, fps, bitrate}`。
- **升级**：先换 Node（向后兼容），再换 CC 脚本；`HELLO.version` 不一致时 CC 必须**明确报错**而不是花屏。
