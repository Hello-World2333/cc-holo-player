# 05 · 部署与运维

## 1. 拓扑

```
公网 VPS
  ├─ caddy / nginx  →  wss://wall.example.com/play
  ├─ node 进程      →  码流分发
  └─ 磁盘           →  /srv/wall/videos/<片名>/{meta.json,video.ccv}

家里 / 机房
  └─ MC 服务器（**不需要端口映射、不需要公网 IP**）
       └─ CC 电脑（**一台**）→ 主动外连 wss
```

**连接方向是 CC 主动外连**：MC 服务器不需要任何入站端口，省掉一大半部署麻烦。

## 2. 公网侧

### 2.1 依赖

| 组件 | 什么时候需要 |
|---|---|
| Node 20+ | 总是（码流分发） |
| ffmpeg（带 libvpx / libx264） | **仅转码时**；只播已转好的 `.ccv` 不需要 |
| caddy 或 nginx | 提供 TLS（`wss://`） |

> 第一版只播一个码流，最省事的部署是：本地转好 `.ccv` 丢上去，VPS 只跑静态+ws 分发。

### 2.2 反向代理要点

```
# caddy
wall.example.com {
    reverse_proxy /play* 127.0.0.1:18755
}
```

- **必须关掉代理的响应缓冲**（nginx: `proxy_buffering off;`），否则帧会被攒着发。
- 超时放宽（`proxy_read_timeout 3600s`），否则空闲时连接被掐。

### 2.3 带宽

| 场景 | 典型码率 | 月度流量（每天 4 h） |
|---|---|---|
| **640×360，块 8 + 图集（当前默认）** | **0.85–1.87 Mbps** | **≈ 0.15–0.35 TB** |
| 640×360，块 8，无图集 | 1.8–3.6 Mbps | ≈ 0.3–0.6 TB |
| 剧烈运动，块 20，无图集 | 8 Mbps | ≈ 1.4 TB |
| 场景切换瞬时峰值 | 37 Mbps（几帧） | 可忽略 |

上面两行是**实测**（文件大小 ÷ 时长，见 `docs/02` §10.1），不是估算。

VPS 的**出口流量计费**是这类项目的真正成本项，比 CPU 重要。

## 3. CC 侧

### 3.1 服务器配置检查表

`config/computercraft-server.toml`：

| 项 | 需要 | 本服当前 |
|---|---|---|
| `http.enabled` | true | ✅ |
| `http.websocket_enabled` | true | ✅ |
| `http.max_websockets` | ≥ 1 | 2048 ✅ |
| `http.rules` 放行目标域名 | 需要 | `host="*" allow` ✅ |
| `max_websocket_message` | ≥ 64 KB | 131072 ✅ |
| `http.bandwidth.global_download` | 够用 | 32 MB/s ✅ |
| `computer_space_limit` | 够放脚本 | 100 MB（**对机架式电脑无效**，见 §3.2） |

> 若将来把 `*` 收紧成白名单，记得把公网域名加进 `host`，否则 CC 连不上。

### 3.2 ⚠️ 机架式电脑的磁盘只有 4 KB

CEE:CC 的**机架式电脑**不走 `computer_space_limit`，它自带一个极小的固定容量：

```
> fs.getCapacity("/")
4096          -- 只有 4 KB，不是配置里的 100000000
```

我们的 `wall.lua` + `decoder.lua` + 配置就接近 9 KB，**放不下**，会报 `out of space`。
（上一代 #80 的 `startup.lua` 里那段 `fs.exists("/padsize")` 就是为这件事留的。）

**扩容办法（已验证，观察自 `computer/81`）**：
CC 的容量统计只在挂载/开机时**按文件名义大小**记一次账，而且不监听宿主机侧的
外部读写，所以可以「先让账面上欠一大笔，再删掉它」把已用量压成负数。

```bash
# 1. 在世界存档里直接操作（服务器可以开着，这些文件在开机时才结算）
cd world/computercraft/computer/81
truncate -s 1073741824 padsize      # 稀疏文件：名义 1 GiB，实际占 0 块
```

```lua
-- 2. startup.lua 第一行必须删掉它
if fs.exists("/padsize") then fs.delete("/padsize") end
shell.run("/wall.lua")
```

```bash
# 3. 重启电脑（Ctrl+R 或 rcon: computercraft shutdown/turn-on 81）
```

实测结果：

| | `fs.getCapacity("/")` | `fs.getFreeSpace("/")` |
|---|---|---|
| 扩容前 | 4096 | 负数 / 0 |
| 扩容后 | 4096 | **1073741332**（≈ +1 GiB） |

- `capacity` 仍是 4096，变的是**已用量成了负数**，于是可用空间凭空多出 1 GiB；
- **跨重启保持**：第二次重启后 `free = 1073740832`，比上次少 500 B，正好是新写的日志。
  即「欠账」是持久的，后续写入从这 1 GiB 里扣；
- 所以**一次就够**，不用每次开机都做（`padsize` 已被删除，再做也无效——改成别的文件名即可再来一次）。

> 💡 **「扩容的黑魔法」** 指的就是这套 `padsize` 流程。项目里提到「充值 / 扩容 / 黑魔法 / 存储不够」
> 时，优先怀疑这个，而不是去改 `computercraft-server.toml`。

### 3.3 CC 电脑准备

```lua
-- /wall.cfg（textutils.serialise 格式，**不带 return**）
{ url = "wss://wall.example.com/play?token=SECRET",
  name = "wall1",
  log = true }
```

```lua
-- /startup.lua
shell.run("/wall.lua")
```

- 电脑要能看到 **hologram**（`peripheral.find("hologram")`；本服 `adjacentLinking = false`，
  贴着放不算连上，必须接 **Peripheral Cable**）。
- **不要**往电脑电子盘放视频文件：机架式电脑只有 4 KB，扩容后也只有 1 GiB，
  而码流本来就只走 ws 不落盘。
- 换脚本后必须重启电脑（CC 只在开机读 `startup.lua`）：游戏内 `Ctrl+R` 或 `computercraft shutdown/turn-on`。
- 重启命令（RCON，本服 `enable-rcon=true`，端口 26768）：

```bash
rcon "computercraft shutdown 81"
rcon "computercraft turn-on 81"
```

### 3.4 延迟

- 公网 RTT 建议 < 150 ms；> 300 ms 时 20 fps 的「1 帧在飞」会变迟钝（可降到 10–15 fps）。

## 4. 转码流程（离线）

```
1. 准备源视频（ffmpeg 能解的任意格式）
2. 转码：  node dist/transcode.js --in movie.mp4 --out /srv/wall/videos/movie \
              --fps 20 --block 8
3. 产物：  movie/meta.json + movie/video.ccv
4. 上传：  rsync 到 VPS
5. 播放：  见下面 §5「跑成服务」
```

> `--block 8` 是图集编码的前提（瓦片就是块网格）。用别的块大小必须加 `--atlas off`，
> 否则转码直接报错退出。transcode 自带逐帧 `encode→decode→对比` 校验，不通过会以
> 退出码 2 终止，所以不再需要单独的 verify 步骤。

### 转码耗时

本机（32 核，Node 22）实测，单线程：

| 源 | 时长 | 耗时 | 相对实时 |
|---|---|---|---|
| 科学-MIMI | 188 s | 68 s | 0.36× |
| 洛天依雨爱 | 263 s | 179 s | 0.68× |

慢的那个是运动剧烈、图集频繁淘汰的素材。若只在乎体积、不在乎时间，把
`--atlas-scan` 调大（512 约再省 10%，不限约省 30%，但会慢到 1.6× 实时）。
取舍表见 `docs/02` §4.2。

`verify` 是**强制步骤**：码流是自定义的，没有「播放器能放就算对」这回事。

## 5. 跑成服务（不要用 nohup）

服务端是个常驻进程，必须挂到用户级 systemd 上。**不要 `nohup ... &`**：
那样崩了不会重启、日志滚不起来、也没有内存上限，而这台机器还要跑 Minecraft。
（本服 SOP 见 `/mnt/data/linyun/RFSO/SOP/服务部署/systemd.md`，一句话：用用户级 systemd。）

```bash
# 一次性安装
cat > ~/.config/systemd/user/cc-video-wall.service <<'UNIT'
[Unit]
Description=CC video wall (ccv stream server, library mode)
After=network-online.target

[Service]
Type=simple
WorkingDirectory=/home/linhui/cc-video-wall
ExecStart=/home/linhui/.nvm/versions/node/v22.23.3/bin/node node/dist/serve.js \
    --library /mnt/data/devshare/cc-holo-player-media \
    --port 18756 \
    --cache /home/linhui/.cache/cc-video-wall
Restart=always
RestartSec=2
KillMode=mixed
MemoryMax=1G

[Install]
WantedBy=default.target
UNIT

systemctl --user daemon-reload
systemctl --user enable --now cc-video-wall.service
```

日常操作：

```bash
systemctl --user status  cc-video-wall        # 状态 + 内存
systemctl --user restart cc-video-wall        # 换了码流/参数之后
journalctl --user -u cc-video-wall -f         # 跟日志
journalctl --user -u cc-video-wall -n 100     # 最近 100 行
```

几个要点：

- **`Restart=always` 是对客户的承诺**：客户端自带看门狗，服务器崩溃重启后
  约 2 秒就能重连，观众只会看到一次短暂的黑屏而不是永久的冻屏。
- **`KillMode=mixed`** 让 systemd 停服务时把它 fork 的 ffmpeg 子进程一起收掉，
  否则换一个视频就漏几个 ffmpeg 在机器上。
- **`--cache ~/.cache/cc-video-wall`** 把媒体库时长和封面存在 home 下而不是
  `/tmp`（本服规则：宁可占 `~/.cache` 也不要在 `/tmp` 堆垃圾）。首次启动会
  探 31 个文件约 1.3 秒，之后 20ms。
- 日志走 journal，不写文件；`SyslogIdentifier` 设成 `cc-video-wall` 方便过滤。

### 与上一代服务共存

`cc-holo-player.service` 是**上一代**项目（`~/cc-holo-player`，端口 18755），
两个可以同时跑，端口不冲突。新项目是 `cc-video-wall.service`（端口 18756）。

## 6. 排障

| 现象 | 先查 |
|---|---|
| CC 连不上 | `http.checkURL("https://…/health")`；`http.rules` 是否放行；证书是否有效（CC 用 Java 信任库，自签会失败） |
| `out of space` / 脚本存不进去 | 机架式电脑只有 4 KB（§3.2）；用 `padsize` 扩容，别改 `computer_space_limit` |
| 脚本写进去了但行为没变 | 电脑没重启；CraftOS 只在开机读 `startup.lua` |
| 连上但黑屏 | `HELLO` 版本是否匹配；`resize` 是否调用；`sync` 是否在调 |
| 花屏/错位 | `block` 与编码器是否一致；`setColorMapping` 是否设置 |
| 启动即报 `atlas: slot N of M refused` | 图集槽分配失败，检查 `wall.log` 的 `hello` 行应含 `atlas=14` |
| 报 `this is a ccv v1 file` | 旧码流，重新转码（v2 改了容器头） |
| 越来越慢 | 对照 `docs/02` 预算表，看是不是 RAW 比例失控（块太大或运动太剧烈） |
| 卡一下再跳变 | 出现全 RAW 帧 ⇒ 需要渐进刷新（`docs/02` §7） |
| 帧率只有一半 | 「1 帧在飞」被 RTT 拖累 ⇒ 考虑 2 帧在飞，或降 fps |

## 7. 运维

- **日志**：CC 端可关（`wall.cfg` 的 `log`）；Node 端走 journal（见 §5）。
- **监控**：`GET /health` 返回 `{ok, clients, mode, videos, uptime}`。
- **升级**：先换 Node（向后兼容），再换 CC 脚本；`HELLO.version` 不一致时 CC 必须**明确报错**。

## 8. 音频（CEE HQ 通道）

音频不走视频那条路：CEE 的 Electric Speaker 有独立的高质量（HQ）通道，**模组自己解码**
（jar 里带 `CEEVorbis`，支持 ogg/wav/mp3/aiff/au），所以服务端只负责产出一条合法的
Ogg 并处理尾部问题。

### 8.1 为什么必须整轨

`speakPCM` 这类调用**每次都是一条独立的声音**，addon 会先 halt 掉同一位置的上一条，
所以逐块喂只能是「每块响一 tick」——上一代播放器踩过这个坑。连续播放只有一条路：

```lua
group.speakOpen("ogg", volume)   -- 开一个会话
group.speakAppend(bytes)         -- 反复追加（单次上限 256 KiB，总量上限 16 MiB）
group.speakEnd()                 -- 才开始播
```

### 8.2 为什么用 group 句柄，以及为什么还要补 8 个

`cee.getSpeakers(pin)` 返回的句柄覆盖**同一条线缆 run**，一次 `speakEnd()` 让它们
同一 tick 起播；独立句柄各成一条声音，会互相错开。服务端日志里那句
`the set of speakers on its cable run changed, so the whole run restarted together`
就是这个「同一条 run 一起走」的机制。

⚠️ **本服实测：pin group 只覆盖 16 个音响里的 8 个。**

这条线物理上是「一条线串到底、一头接 signal4」，但 `getSpeakers({8,4}).getCount()`
只报 **8**，而按索引能取到 **16** 个句柄。用不同音高分别驱动两组、让人耳判断，
结果很干净：

| 驱动方式 | 响的位置 |
|---|---|
| pin group | 右边 8 个 |
| 索引 1–8 | 右边 8 个（和 group 同一批） |
| 索引 9–16 | **左边 8 个**（哑的那半） |

所以 `cc/audio.lua` 启动时会在 group 之后继续按索引探测，把多出来的句柄作为
`extras` 一起驱动：`speakOpen` → 逐块 `speakAppend` → 在同一 tick 里紧接着 group
`speakEnd`。分处不同 tick 会有可闻的延迟，所以必须同 tick 收尾。

实测 2.28 MB 整轨分发到 1 组 + 8 个 extras 用 **154 ms**（只发 1 组是 74 ms）——
addon 按内容哈希去重，逐个分发很便宜。9 个会话的 `speakEnd` 在 **1 ms** 内完成。

探测要**遇到第一个缺失就停**：`getSpeakers` 每次是一次 hub 查找，在 CraftOS 上很贵，
遍历 64 个槽位会让启动卡住一分多钟（踩过）。

如果哪天接线改了、16 个都在 group 里，`extras` 自然为空，不需要改配置。
要强制关掉可以设 `audioExtras=false`。

### 8.3 实测参数（本服，hub 8 pin 4，8 个音响）

| 项 | 值 |
|---|---|
| `speakSampleRate` | 48000 |
| `speakMaxBytes` | 8388608（8 MiB，单次传输） |
| `speakMaxSessionBytes` | 16777216（16 MiB，流式会话） |
| `speakSupportedFiles` | wav, ogg, aiff, aif, au, snd, mp3 |
| `getVoltageFactor` | ≈0.63（线路电压决定音量上限） |
| `CEEHqLimits.MAX_APPEND_BYTES` | 262144（单次 append，超了抛异常且整轨丢失） |
| `CEEHqLimits.MAX_DECODED_BYTES` | 67108864（解码后，≈11.6 分钟） |
| `CEEHqLimits.SEND_RADIUS` | 48 格（玩家在此半径外听不到） |

实测：2.28 MB 分 70 片追加，**耗时 74 ms**；`speakAppend` 很便宜，瓶颈不在 CC 端。

### 8.4 尾部 4 秒

症状：HQ 轨道最后约 4 秒被静音。社区给的解法是**在末尾补 4 秒静音**，服务端默认就这么做
（`--audio-pad 4`）。它成立的前提是截断发生在流末尾，而补白正好把那 4 秒填掉：
音轨比视频长 4 秒，视频结束时刚好是「本来会被吃掉」的那段开始的地方。

⚠️ 这是**缓解不是根治**。如果换片源后仍听到尾部缺失，先确认是不是这个 bug 变了形状，
而不是怀疑链路。

### 8.5 同步启动

视频编码器首帧要 1.4–2.9 秒。如果音频一 stage 就播，声音会领先画面这么久。所以顺序是：

1. 服务端推完整条音轨（`AUDIO_OPEN` / `AUDIO_CHUNK`×N / `AUDIO_DONE`）
2. CC 全部 append 完，回 `AUDIO_READY`
3. 服务端启动视频编码器，**首帧就绪时**发 `AUDIO_START` → CC 调 `speakEnd()`

实测 `AUDIO_START` 与首帧相差 **0–1 ms**。

**音频永远不能阻塞视频**：CC 若报 `AUDIO_READY status != 0`（没有音响 / append 失败），
服务端照常开播；等待也有 5 秒超时。

### 8.6 配置与排查

`wall.cfg` 里加 `audioHub=8, audioPin=4, audioVolume=1.0`（不给就自动扫 hub 和 1..9 号脚，
取音响最多的那一组）。

```bash
journalctl --user -u cc-video-wall -f | grep audio
```

关键日志：`audio: staged on client in Nms`、`audio: start sent with first frame`。
CC 端 `/wall.log` 里应有 `audio: 8 speaker(s) on hub 8 pin 4`。

注意 `speakIsPlaying()` 在本服**不可信**（播着也返回 false），不要拿它做判据，用耳朵。
