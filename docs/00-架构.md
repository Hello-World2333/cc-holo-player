# 00 · 架构

> **2026-11-15 定稿**：第一版是**一块 640×360 全息屏 + 一台电脑**。
> 依据见 [`adr/0007`](adr/0007-一块全息屏只能接一台电脑.md)——反编译证明
> 一个 hologram 方块只有一个外设实例，「当前激活缓冲」是它上面的单个字段，
> 所以多台电脑共享一块屏会互相踩。单机还顺带消除了上一代 4 台分工的**存在理由**（见 §5）。

## 1. 目标与非目标

**目标**

- 在 VoidPower `hologram` 上播放视频，**640×360 @ 20 fps**。
- 编码在**公网**，解码在**游戏内 CC**。MC 服务器那台机器**不新增任何依赖**。
- 一块屏装不下更高分辨率时（> `getMaxBufferSize()` = 393216 像素，即约 640×360 以上），
  能扩展到多块屏（见 `04`）。

**非目标（第一版）**

- 音频（架构里留位置，先不做）。
- 屏上 GUI / 视频库 / 缩略图。
- 多面墙、多会话、多用户。
- 实时转码任意视频（第一版离线转成 `.ccv`）。
- 兼容标准 VP8/VP9/H.264 码流（**做不到**，见 `docs/02` 与 ADR-0002）。
- **多台电脑分工一块屏**（不可行，见 ADR-0007）。

## 2. 两台机器、职责边界

| 角色 | 在哪 | 装什么 | 职责 |
|---|---|---|---|
| **Node 服务** | 公网 VPS | Node（+ ffmpeg，仅转码时用） | 把视频变成 `.ccv`；通过 wss 分发；维护播放状态 |
| **MC 服务器** | 另一台机器 | **不装任何东西** | 只提供 CC 的 `http.websocket` 出口 |
| **CC 电脑** | 游戏内，**一台** | Lua 脚本（电子盘） | 解码整帧；blit 到 hologram；`sync()` |

> 与上一代的根本区别：上一代在 MC 宿主上跑 Node+ffmpeg 实时转码、推 raw 帧、
> 由 4 台 CC 各画一块；现在 MC 宿主只是「一个普通 MC 服务器」，游戏内只有一台 CC。

## 3. 通道

| 通道 | 承载 | 载体 | 量级 |
|---|---|---|---|
| **像素通道** | 压缩码流 | CC `http.websocket` → 公网 wss | 典型 3.7 Mbps，峰值 37 Mbps |
| ~~同步通道~~ | ~~fabric ack/栅栏~~ | — | **第一版不需要**（只有一台电脑，见 §6） |
| **音频通道**（未实现） | 48 kHz s8 PCM | CC ws + CEE 音响组 | 48 KB/s/路 |

**为什么像素不走 fabric**：`CEENetwork.sizeOf(String) = 16 + 2N`（**UTF-16 计费**），
`bulkTokensPerTick = 8` 是**每台发送机**的额度 ⇒ 实际像素吞吐 ≈ **0.58 MB/s**，
而本项目的典型码流就是 0.46 MB/s。零余量，且超限表现为「静默拒收」。详见 [`adr/0004`](adr/0004-fabric只跑控制.md)。

**为什么像素可以走 ws**（`config/computercraft-server.toml`）：

| 配置项 | 值 |
|---|---|
| `http.enabled` / `websocket_enabled` | `true` / `true` |
| `max_websocket_message` | **131072** 字节 |
| `http.bandwidth.global_download` | 33554432 B/s |
| `max_websockets` | 2048 |
| `http.rules` 的 host `*` | `action = "allow"` |

⇒ 单消息 < 128 KB，总带宽不是瓶颈。一帧全 RAW 有 230 KB，用**分片帧**（`part`/`parts`）拆开，见 `docs/01` §5。

## 4. 一帧的完整生命周期

```
[公网 Node]
  1. 从 .ccv 读出第 N 帧（或实时编码），按 16×16 块组织
  2. 若单帧 > 48 KB，拆成 parts 条消息依次发
  3. 等 CC 的 ACK(N) 再发 N+1（1 帧在飞）

[CC（就一台）]
  4. 收 parts，拼齐后用块数据更新**显示缓冲**
       MV  → h.blitFrameBufferArea(dx,dy,sx,sy,w,h,prevId)   ← Java memcpy
       RAW → h.blit(x,y,w,h,table)                           ← 唯一用到 Lua 表的地方
  5. 把显示缓冲的整块区域拷进 prev framebuffer（一条 Java 调用）
  6. h.sync()          ← 上屏
  7. 回 ACK(N)
```

## 5. 为什么解压必须由 CC 自己干

| 方案 | 公网带宽（640×360@20） | MC 机器依赖 | CC 算力 |
|---|---|---|---|
| raw 直发 | 37 Mbps 持续 | 无 | 只需 blit（71 ms/帧，**20fps 做不到**） |
| MC 本机代理解码 + 局域网 raw | 公网 1–3 Mbps | **要装 node/ffmpeg** | 只需 blit（同样 71 ms） |
| **CC 自己解码（本项目）** | 典型 3.7 Mbps | **无** | 解码 + blit，**典型 18 ms** |

上一代选了第二种（宿主机代理）。它之所以需要 4 台 CC，是因为传的是 raw 全帧，
每台 `blit` 320×180 就要 18 ms——**分工是为了绕过 blit 成本**。

### 5.1 关键杠杆：运动补偿在 Java 侧

反编译 `void_power-1.0.7.fix2.jar` 发现 hologram 外设提供
`blitFrameBufferArea(dx,dy,sx,sy,w,h,bufferId)`，是**纯 Java 的逐字节拷贝**；
而 `blit(x,y,w,h,table)` 每像素要做 2 次 `Double` 装箱 + 2 次 `HashMap` 查找。

把上一帧存进另一个 framebuffer，「运动补偿」就变成**一次 Java 调用**（几微秒）。
于是每帧成本 **∝ 新露出的像素数**，而不是 ∝ 像素总数。

⇒ **4 台电脑的主要理由消失了。** 单机典型 18 ms，20 fps 有余。详见 [`adr/0006`](adr/0006-MV用帧缓冲拷贝.md)。

## 6. 为什么第一版不需要 fabric

上一代用 fabric 在 4 台机器间做 ack 栅栏（同一帧全部画完才 sync）。
现在只有一台电脑，**帧序天然一致，自己画完自己 sync**。

fabric 仍然保留在架构里（ADR-0004），但**第一版一行都不用**。
将来上多块屏（`04` §4）时才会启用。

## 7. 离线转码 vs 实时转码

第一版**只做离线**：

|  | 离线 `.ccv` | 实时 |
|---|---|---|
| 延迟 | 首帧即出（可 seek） | ffmpeg 启动 + 预缓冲 1–2 s |
| 服务器 CPU | 只有 IO | 每路一个 ffmpeg + 编码 |
| 可测试性 | **完全可以离线逐像素比对** | 难复现 |
| 换片 | 后台转好再切 | 立刻 |

离线带来本项目唯一的正确性保障：**编码器可以精确模拟解码器**，逐帧校验像素一致。

## 8. 仓库布局

```
cc-video-wall/
├── docs/            设计与决策（先写文档，后写代码）
├── node/            公网侧：transcoder（离线）+ server（码流分发）
├── cc/              游戏内 Lua：decoder / renderer
└── tools/           基准、码流分析、逐帧对比
```

单包，不发布 npm（`"private": true`），`tsc` + `node dist/` 即可，不需要 workspace。

## 9. 命名与术语

| 术语 | 含义 |
|---|---|
| **wall** | 一面墙（第一版 = 一块 hologram = 640×360） |
| **region** | 一块 hologram 上的矩形区域；第一版就是整块（`0,0,640,360`） |
| **frame** | 一帧画面，带 `seq`；可能由多条 `part` 消息组成 |
| **block** | 解码单元，第一版 **16×16**（回退 32×32，见 `02` §5） |
| **prev** | 上一帧，存在 hologram framebuffer 里（`prevId`），不占 Lua 内存 |
| **ccv** | 本项目自定义的码流容器（`.ccv` 文件 / ws 消息同构） |
| **KEY** | 整帧重建（所有块 RAW），用于首帧与场景切换 |
