# 00 · 架构

## 1. 目标与非目标

**目标**

- 在 VoidPower `hologram` 上播放视频，画面可以**多屏拼接**成更高分辨率（第一版 2×2 = 640×360）。
- 编码在**公网**，解码在**游戏内 CC**。MC 服务器那台机器**不新增任何依赖**。
- 单屏 20 fps 为设计目标（与上一代一致），可配置降级。
- 多块屏之间不撕裂：同一帧的所有分区**同时**上屏。

**非目标（第一版）**

- 音频（架构里留位置，先不做）。
- 屏上 GUI / 视频库浏览 / 缩略图（第一版只播一个码流）。
- 多面墙、多会话、多用户各自播放。
- 实时转码任意视频（第一版建议离线转码成 `.ccv`，见 §6）。
- 兼容标准 VP8/VP9/H.264 码流（**做不到**，见 `docs/02` 与 ADR-0002）。

## 2. 三台机器、职责边界

| 角色 | 在哪 | 装什么 | 职责 |
|---|---|---|---|
| **Node 服务** | 公网 VPS | Node（+ ffmpeg，仅转码时用） | 把视频变成 `.ccv` 码流；通过 wss 分发给各 CC；维护播放状态 |
| **MC 服务器** | 另一台机器 | **不装任何东西** | 只提供 CC 的 `http.websocket` 出口 |
| **CC 电脑** | 游戏内 | Lua 脚本（电子盘） | 解码自己那一块；blit 到 hologram；fabric 同步 |

> 这条边界是本项目与上一代的**根本区别**：上一代在 MC 宿主上跑了一个 Node+ffmpeg 的实时转码进程，还要把 raw 帧推过 ws；
> 现在 MC 宿主只是一个「普通 MC 服务器」。

## 3. 三条通道

| 通道 | 承载 | 载体 | 量级 |
|---|---|---|---|
| **像素通道** | 压缩码流（`.ccv` 的帧） | CC `http.websocket` → 公网 wss | 每屏 0.5–2 Mbps（典型） |
| **同步通道** | 帧号、播放态、按键 | CEE:CC `fabric`（金脚+Peripheral Cable） | 每帧几字节 |
| **音频通道**（未实现） | 48 kHz s8 PCM | CC ws（`role=audio`）+ CEE 音响组 | 48 KB/s/路 |

**为什么像素不走 fabric**：`CEENetwork` 的额度是**每台发送机**的——`bulkTokensPerTick=8`、`bulkBytes=512`，
即单机约 8 条大包/tick ≈ 1.15 MB/s，而且接收方每 tick 只交出 32 条事件（`ingressDrainPerTick`）。
一块 320×180@20fps 的原始码流就是 1.15 MB/s，**刚好占满且零余量**，还不能多个接收方共享同一份发送额度
（额度按发送计，不按接收计）。所以 fabric 只用来传控制信息。

**为什么像素可以走 ws**：CC 的 `http` 限制远宽于需求：

| 配置项（`config/computercraft-server.toml`） | 值 |
|---|---|
| `http.enabled` / `websocket_enabled` | `true` / `true` |
| `max_websocket_message`（`*` 规则） | **131072** 字节 |
| `http.bandwidth.global_download` | 33554432 B/s |
| `max_websockets` | 2048 |
| `http.rules` 的 host `*` | `action = "allow"` |

即：**单个 ws 消息必须 < 128 KB**（我们的分片按 4–8 KB 设计，天然满足），总带宽不是瓶颈。

## 4. 数据流（一帧的完整生命周期）

```
[公网 Node]
  1. 从 .ccv 读出第 N 帧的分区数据（或实时编码出来）
  2. 按 region 分别发给 4 台 CC 的 wss（帧头带 seq=N）
        │
        ├──▶ CC#A (region=0,0)      解左上
        ├──▶ CC#B (region=320,0)    解右上
        ├──▶ CC#C (region=0,180)    解左下
        └──▶ CC#D (region=320,180)  解右下

[CC 侧，每台]
  3. 收到帧消息 → MV 走 Java 帧缓冲拷贝、RAW 走 blit 表（见 docs/02 §4）
  4. 直接画进显示缓冲（**全局坐标**，如 #B 写 x=320..639）
  5. 把本区域存进自己的 prev framebuffer（一条 Java 拷贝）
  6. 通过 fabric 给 master 回 `ack(seq)`

[master（可以是其中一台，也可以单独一台）]
  7. 收到 4 个 ack 且 seq 一致 → h.sync()  ← **只有它 sync**
  8. 通过 fabric 广播 `go(seq+1)`（可选：也可以由 Node 直接控制节奏）
```

**关键**：4 台写的是**同一张** hologram 缓冲（640×360 = 230400 px ≤ `getMaxBufferSize()=393216`），
只是各写各的坐标区间。所以「拼接」在物理上是**共享帧缓冲 + 分区写入**，不是把 4 张图拼起来。
上一代已经用这个方法跑了 640×360，`render.lua` 里 `[78]={320,0,320,180}` 就是直接写全局坐标。

## 5. 为什么必须让 CC 解码

| 方案 | 公网带宽（640×360@20） | MC 机器依赖 | CC 算力 |
|---|---|---|---|
| raw 直发 4 台 | 37 Mbps 持续 | 无 | 只需 blit |
| MC 本机代理解码 + 局域网 raw | 公网 1–3 Mbps | **要装 node/ffmpeg** | 只需 blit |
| **CC 自己解码（本项目）** | 公网 1–6 Mbps | **无** | 解码 + blit |

上一代选了第二种（宿主机代理），本项目选第三种。代价是 CC 必须用**自己的算力**解压，
而 CC 的 Lua 很慢（见 `docs/02` 的实测），于是**码流必须为 Lua 定制**——这是本项目最核心的设计约束。

### 5.1 关键杠杆：运动补偿在 Java 侧

反编译 `void_power-1.0.7.fix2.jar` 后发现 hologram 外设提供
`blitFrameBufferArea(dx,dy,sx,sy,w,h,bufferId)`，是**纯 Java 的逐字节拷贝**；
而 `blit(x,y,w,h,table)` 每像素要做 2 次 `Double` 装箱 + 2 次 `HashMap` 查找。

于是把上一帧存在另一个 framebuffer 里，「运动补偿」就变成**一次 Java 调用**。
这让每帧成本变成 **∝ 新露出的像素数**，而不是 ∝ 像素总数。详见 [`adr/0006`](adr/0006-MV用帧缓冲拷贝.md)。

## 6. 离线转码 vs 实时转码

两种都保留，但第一版**推荐离线**：

|  | 离线 `.ccv` | 实时 |
|---|---|---|
| 延迟 | 首帧即出（可 seek） | ffmpeg 启动 + 预缓冲 1–2 s |
| 服务器 CPU | 只有 IO | 每路一个 ffmpeg + 编码 |
| 可测试性 | **完全可以离线对比解码正确性** | 难复现 |
| 换片 | 后台转好再切 | 立刻 |
| 码率 | 可以两遍、可以逐帧调参 | 只能单遍 |

离线还带来一个关键好处：**编码器可以精确模拟解码器**（同一套整数逻辑，逐帧校验像素一致），
这在「自己发明码流」的项目里是唯一的正确性保障。

## 7. 仓库布局

```
cc-video-wall/
├── docs/            设计与决策（先写文档，后写代码）
├── node/            公网侧：transcoder（离线转码）+ server（码流分发）
├── cc/              游戏内 Lua：decoder / renderer / master
└── tools/           基准、码流分析、逐帧对比
```

单包，不发布 npm（`"private": true`），`node/` 里直接 `tsc` + `node dist/` 运行即可，不需要 workspace/monorepo。

## 8. 命名与术语

| 术语 | 含义 |
|---|---|
| **wall** | 一面墙（一组拼接的 hologram 区域） |
| **region** | 一台 CC 负责的矩形区域，全局坐标 `x,y,w,h` |
| **frame** | 一帧画面，带 `seq` |
| **block** | 码流的解码单元，第一版 **16×16**（见 `docs/02` §5） |
| **prev** | 上一帧，存在 hologram framebuffer 里（`prevId`），不占 Lua 内存 |
| **ccv** | 本项目自定义的码流容器（`.ccv` 文件 / ws 消息同构） |
| **master** | 负责 `h.sync()` 与 fabric 栅栏的那台 CC |
