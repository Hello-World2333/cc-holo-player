# 03 · CC 端设计

一台 CC = 一台渲染机，画**整个** 640×360 全息屏（v1 单屏，不做拼接）。
另有一块「控制屏」同样是全息屏，挂在 CEE data hub 的插口上，用来调参数。

> 2026-11-15 修订：`prev` 存在 **hologram framebuffer** 里，不再用 Lua 字符串；
> MV 走 `blitFrameBufferArea`。见 [`adr/0006`](adr/0006-MV用帧缓冲拷贝.md)。

## 1. 主循环形状

```
启动
 ├─ 找视频 hologram（peripheral.find("hologram")）
 ├─ 找控制 hologram（cee.getPeripheral{hub, pin}，见 §11）
 ├─ releaseAllFrameBuffer()            ← 必须！否则历次重启会占满 16 个槽位
 ├─ 连 wss（URL 带 token）
 ├─ 收 HELLO → resize(wall_w, wall_h) + setColorMapping
 │             + prevId = allocateFrameBuffer(region_w, region_h)
 └─ 事件循环：
      websocket_message → FRAME / CONTROL / PING
      websocket_closed  → 2 s 后重连（丢弃 prev，等 KEY 帧）
      timer             → 保活/重连/统计（**不能依赖它驱动解码**）
```

## 2. 解码一帧

状态只有两个数字：

| 变量 | 值 | 说明 |
|---|---|---|
| `prevId` | framebuffer id | 上一帧的整块区域（`region_w × region_h`），**在 Java 堆里** |
| `regionX/Y/W/H` | 来自 `HELLO` | 全局缓冲坐标 |

```lua
local function decodeFrame(msg)
    local pos = 8                       -- 跳过 type/seq/flags/bx/by
    local bx, by = byte(msg,5), byte(msg,6)
    local B = BLOCK
    local bitmapBytes = math.ceil(bx * by / 8)
    pos = pos + bitmapBytes

    h.activateFrameBuffer(-1)           -- 目标 = 显示缓冲（只需一次）
    for i = 0, bx * by - 1 do
        if bitAt(msg, 9, i) then
            local mode = byte(msg, pos); pos = pos + 1
            local px = (i % bx) * B + regionX
            local py = (i // bx) * B + regionY
            if mode == 1 then           -- MV
                local dx = byte(msg, pos) - 128
                local dy = byte(msg, pos + 1) - 128
                pos = pos + 2
                h.blitFrameBufferArea(px, py, px - regionX + dx, py - regionY + dy, B, B, prevId)
            elseif mode == 2 then       -- RAW
                local tbl = buildTable(sub(msg, pos, pos + B * B - 1))
                pos = pos + B * B
                h.blit(px, py, B, B, tbl)
            else
                error("unknown mode " .. mode)
            end
        end
    end
    -- 把本区域从显示缓冲存进 prev（一条 Java 调用，region_w*region_h 字节）
    h.activateFrameBuffer(prevId)
    h.blitFrameBufferArea(0, 0, regionX, regionY, regionW, regionH, -1)
    h.activateFrameBuffer(-1)
end
```

成本（320×180，16×16 块，240 块）：

| 部分 | 成本 |
|---|---|
| bitmap 扫描 + 循环（240 次） | ~0.5 ms |
| MV 调用（典型 200 块） | 200 × ~10 µs = **~2 ms** |
| RAW 调用（典型 10% 像素 ≈ 23 块） | 23 × (0.04 建表 + 0.04 blit) ≈ **~2 ms** |
| 帧末 prev 保存（1 次 Java 拷贝） | ~0.1 ms |
| **合计** | **~5 ms**（最坏全 RAW ≈ 21 ms） |

## 3. Lua 侧只保留「表构建」

唯一需要 Lua 逐像素处理的地方是 RAW 块的 `bytes → table`。
沿用上一代验证过的写法（16 个一批读，比 `perByte` 快 3 倍）：

```lua
local function buildTable(s)
    local t = {}
    local n, i, base = #s, 0, 1
    while i <= n - 16 do
        local b1, b2, b3, b4, b5, b6, b7, b8,
              b9, b10, b11, b12, b13, b14, b15, b16 = byte(s, base, base + 15)
        t[i] = b1; t[i+1] = b2; t[i+2] = b3; t[i+3] = b4
        t[i+4] = b5; t[i+5] = b6; t[i+6] = b7; t[i+7] = b8
        t[i+8] = b9; t[i+9] = b10; t[i+10] = b11; t[i+11] = b12
        t[i+12] = b13; t[i+13] = b14; t[i+14] = b15; t[i+15] = b16
        i = i + 16; base = base + 16
    end
    while i < n do t[i] = byte(s, base); i = i + 1; base = base + 1 end
    return t
end
```

注意 `blit` 的索引是**从 0 开始的线性索引** `(y-ay)*w + (x-ax)`，
所以 `t[0]` 是第一个像素（见 `adr/0006` 的字节码证据）。

**每个 RAW 块一个小表，用完立刻置 nil。** 绝不留长引用。

## 4. CC 的事件陷阱（上一代的血泪）

1. **hologram 的主线程 API 会吞事件**：`resize/setScale/setColorMapping` 期间排队事件可能丢。
   ⇒ 解码循环用**消息到达驱动**，服务器每 200 ms 的 `PING` 就是为此存在。
2. **framebuffer 存在方块实体里，电脑重启不释放**：上一代因此把槽位占满。
   ⇒ 启动时 `releaseAllFrameBuffer()` 再分配（但要先确认 §7 的共享实例问题！）。
3. **`resize` 会重新 `new byte[w*h]`**（内容丢失）且自动 sync：只在 HELLO 时调一次。
4. **`activateFrameBuffer(-1)` 切回显示缓冲**；每帧切换 2 次（画完切到 prev，存完切回）。
5. **`sync()` 只由 master 调**，且它会 zlib 压缩整块缓冲（1–2 ms）——每帧一次，不要多。

## 5. 内存与 GC

现在的分配量比初稿小得多：

| 每帧分配 | 大小 |
|---|---|
| 收包字符串 | ≤ 58 KB |
| RAW 块临时表 | 23 个 × 256 项 ≈ 十几 KB |
| 临时子串 `sub` | 每块 256 B |

- 临时表用完即 `nil`；
- 不要 `table.concat` 建大字符串；
- 目标：单帧峰值分配 < 100 KB。

## 6. 启动与配置

沿用上一代的「纯数据配置文件」（`textutils.serialise` 格式，**不带 `return`**）：

```lua
-- /wall.cfg
{ url    = "ws://127.0.0.1:18756/play?token=dev",
  name   = "mimi",
  log    = true,
  ctlHub = 8,     -- 控制屏所在 data hub 的 id
  ctlPin = 3,     -- 控制屏所在的插口
  gui    = true } -- false = 不画控制屏
```

- `startup.lua` 只做两件事：删掉 `padsize`（§3.2 的扩容黑魔法），跑 `/wall.lua`。
- **服务器是权威**：尺寸、块大小、fps 全由 `HELLO` 下发，不手抄。
- 部署完必须 `chmod 644`：Minecraft 服务端不是复制文件的账号，而 CraftOS 把
  「无权限」报成 `file not found`，会浪费一整轮排查。

## 7. 共享 hologram 实例（已定案）

原担心多台电脑共享同一个 `HoloFrameBufferManager`。v1 只有一台电脑，不存在这个问题；
`releaseAllFrameBuffer()` 在启动时照常调用，清掉历次重启残留在 16 个槽位里的缓冲。

如果以后回到多机拼接，见 [`adr/0007`](adr/0007-一块全息屏只能接一台电脑.md)：
一块全息屏只能被一台电脑的 `peripheral.wrap` 拿到。

## 8. 自检与日志

| 日志行 | 内容 | 何时 |
|---|---|---|
| `boot` | 电脑 id、hologram 是否存在、`getMaxBufferSize`、已有 framebuffer | 启动 |
| `hello` | 版本、块大小、wall 尺寸、region、fps、`prevId` | 收到 HELLO |
| `frame` | 每 150 帧：`ms`、`raw 块数`、`mv 块数`、`bytes` | 周期 |
| `slow` | 单帧 > 25 ms 时打印明细 | 触发时 |
| `err` | 任何 `pcall` 失败 | 即时 |

`seq` 不连续要能区分：**服务器跳帧**（正常）与**自己漏消息**（异常，需重连）。

## 9. 失败与恢复

| 情况 | 处理 |
|---|---|
| ws 断开 | 2 s 后重连；重连时 prev 内容失效 ⇒ 等 `KEY` 帧 |
| 单帧解析越界（码流损坏） | 丢弃并断开重连，不要带病继续画 |
| `blit` 报错 | 重新 `peripheral.find("hologram")`；连续 3 次失败 `os.reboot()` |
| 30 s 无任何消息 | 主动断开重连 |
| `allocateFrameBuffer` 返回 -1 | 说明 16 个槽位满了 ⇒ `releaseAllFrameBuffer()` 后重试（注意共享风险） |

## 10. master 的额外职责（v1 不适用）

v1 只有一台电脑，没有 master/从机之分，`h.sync()` 由唯一的播放进程自己调。
多机方案留档在 [`04-多屏拼接与同步.md`](04-多屏拼接与同步.md)。

## 11. 控制屏与设置页

需求：**视频在 A 屏，设置界面在 B 屏**，用 CEE data hub 上接的键盘操作，
参数持久化。B 屏也是一块 VoidPower 全息屏（不是 CC monitor）。

### 11.1 两块屏各自独立

| 屏 | 怎么拿到外设 | 变换参数 |
|---|---|---|
| 视频屏 | `peripheral.find("hologram")`（贴在电脑的 `back`） | `settings.main` |
| 控制屏 | `cee.getPeripheral{hubId, pin}` | `settings.ctl` |

两者**互不影响**：改控制屏的偏移不会动视频，反之亦然。`HologramTE` 的
`setOffset/setRotation/setScale` 本来就是每方块一份。

### 11.2 关键约束：全息屏上的中文必须写字面量转义

`P_HologramPeripheral.drawText` 只在 `setUnicodeMode(true)` 时调用
`ParamUtils.unicodeToStr`，而它的正则是 `(\\u(\p{XDigit}{4}))`，
只认**字面反斜杠**：

```lua
h.drawText(0, 0, "\\u504F\\u79FB", 0xFF)   -- ✅ 画出「偏移」
h.drawText(0, 0, "偏移", 0xFF)                  -- ❌ 两个「未知字形」方框
```

实测：`\u504F` → 71 个亮像素的真字形；直接传 UTF-8 → 38 像素的两个方框；
私有区码点 `\uE000` → 19 像素的单个方框。所以「中文能显示」这个结论不能靠
肉眼在远处看，必须比对像素数或字模。

### 11.3 像素格式与配色

和视频通路同一个格式：一字节 = `RRGGBBAA`，每通道 2 bit。
**A=0 是不可见的**，所以要「黑色」也得写 `A=3`（`0x03`）。

### 11.4 字体度量（实测定值）

| 量 | 值 |
|---|---|
| 字形高 | 11 px |
| `drawText(x, y)` 的字形顶部 | `y + 5` |
| ASCII 步进 | 8 px |
| 全角（中日韩）步进 | 16 px |
| 建议行高 | 18 px |

注意 `drawText` 的 `y` 不是字形顶，排版时要减 5；否则每行会慢慢往下漂。

### 11.5 交互

| 键 | 作用 |
|---|---|
| ↑ / ↓ | 选项 |
| ← / → | 粗调（偏移 0.05 格、角度 5°、缩放 0.05） |
| `[` / `]` | 精调（0.01 / 1° ） |
| `r` | 当前项复位 |
| `0` | 本屏全部复位 |
| Tab | 切换「主屏 / 控制屏」 |
| `q` | 收起面板（再按 `q` 或 Tab 唤回，空白屏） |

方向键与 Tab 走 `key` 事件，字母和括号走 `char` 事件。这样分是因为 CC 的
`keys` 表里标点常量的名字不可靠（`leftBracket` 之类），而 `bios.lua` 自己
只用 `keys.enter/left/right/up/down/backspace/home/delete/tab`。
键盘本身通过 CEE 接在 hub 上，产生的是**标准** `key`/`char` 事件
（`CEEComputerKeyboard.keyDown` → `UserComputerInput.keyDown`），没有自定义事件名。

### 11.6 持久化

写 `/settings.cfg`，格式 `屏名.键=值`：

```
main.ox=0.0000
main.scale=1.0000
ctl.ox=0.0000
```

- 每次改动**立即**落盘，没有「保存」步骤可忘。
- 文件损坏/缺失 ⇒ 用默认值启动，绝不让设置文件拦住播放。
- 为什么不用方块 NBT：`HologramTE` 确实把 `offset`/`rot`/`scale` 存进 NBT 了，
  但外设**没有任何 getter**，读不回来。所以这个文件是唯一真源，开机按它 apply。

### 11.7 越界值是静默丢弃的

`HologramTE.setOffset` 对 `|v| > 8`、`setScale` 对 `(0, 4]` 之外的值，
都是 `ifeq` 直接跳到 `return`：**不抛异常、不钳制、不报错**。
所以 `settings.clamp` 不是装饰——不钳制的话界面在动、屏幕不动，没有任何提示。
