# 03 · CC 端设计

一台 CC = 一个渲染机，只负责自己那块 `region`。第一版 2×2，全局 640×360，每块 320×180。

## 1. 主循环形状

```
启动
 ├─ 找 hologram（peripheral.find / cee.getPeripherals 兜底）
 ├─ 连 wss（URL 带 token）
 ├─ 收 HELLO → resize(640,360) + setColorMapping + 记下 region
 └─ 事件循环：
      websocket_message  → FRAME / CONTROL / PING
      websocket_closed   → 2 s 后重连
      timer              → 保活/重连/统计（**不能依赖它驱动解码**，见 §4）
```

## 2. 解码一帧（P1）

状态：

| 变量 | 类型 | 大小 | 说明 |
|---|---|---|---|
| `prev` | string | 57.6 KB | 上一帧整块区域（行优先，1 B/px） |
| `cur` | string 或逐块处理 | — | 见下 |
| `seq` | number | — | 上一帧帧号 |

处理顺序（**必须先把整帧解完再统一 blit？不，可以逐瓦片 blit**，因为每个瓦片只写自己的矩形）：

```
for 每个 bitmap 置位的瓦片 (tile 索引 t)：
    mode = byte
    if mode == RAW:
        px = sub(msg, pos, pos+4095)              -- 1 次 sub，C 侧
        tbl = buildTable(px)                      -- 0.7 ms
        h.blit(gx, gy, 64, 64, tbl)               -- 0.6 ms
        把 px 写回 cur 的对应位置（供下一帧的 prev 用）
    if mode == MV:
        for row in 0..63:
            seg = sub(prev, (sy+row)*W + sx + 1, ... + 63)   -- 1 次 sub/行
            rows[row] = seg
            cur 写入同样一行
        tbl = buildTable(concat(rows))             -- 0.7 ms
        h.blit(gx, gy, 64, 64, tbl)                -- 0.6 ms
未置位的瓦片：不动（hologram 上保持上一帧的像素）
prev = cur
send ACK(seq)
```

成本（P1，320×180）：`RAW` 瓦片 1.3 ms，`MV` 瓦片 1.3 ms + 64 次 sub（≈0.2 ms）。
典型帧 5 个瓦片变化 ≈ **7 ms**；全变 15 块 ≈ **22 ms**。

**核心优化（必须做）**：维护 `cur` 只在瓦片粒度做字符串拼接，**避免整帧 57600 次表写入**。
如果偷懒每帧重建整帧表，成本固定 10 ms 且无法「跳过不变瓦片」。

## 3. `cur` 怎么拼得动

`cur` 是 320×180 的字符串。按瓦片就地改写它需要「字符串按偏移替换」——
Lua 字符串不可变，只能 `sub(1,a-1) .. new .. sub(b+1)`，每改一块是全串拷贝（57.6 KB memcpy，C 侧，很快）。

P1 每帧改 k 个瓦片 ⇒ k 次整串拼接。0.1–0.3 ms/次 ⇒ 5 块 ≈ 1 ms。可接受。

> 替代方案：`cur` 用「按行的表」`rows[y] = 该行字符串`（180 行）。
> 改一块瓦片 = 改 64 行的 `sub` 拼接（180 行里 64 行），每行 320 B 拷贝。
> 更省：改一行只拷贝 320 B 而不是 57.6 KB。**推荐这个**，见 `docs/06` 待测项。

## 4. CC 的事件陷阱（上一代的血泪）

1. **hologram 的主线程 API 会吞事件**：调用 `setScale/resize/setColorMapping` 期间，排队的事件可能丢。
   ⇒ 解码循环不要依赖「每秒 N 次 timer」，要用**消息到达驱动**（服务器每 200 ms 的 `PING` 就是为此）。
2. **`allocateFrameBuffer` 的缓冲存在方块实体里，电脑重启不释放**：上一代因此把槽位占满。
   ⇒ 第一版**不用 framebuffer**，直接 blit 到显示缓冲。
3. **`resize` 会自动 sync**：所以只在 HELLO 时 resize 一次，别每帧调。
4. **`sync()` 只由 master 调**（见 `docs/04`），渲染机不要调，否则会互相打断。

## 5. 内存与 GC

Lua 的 GC 在 CC 上很贵。每帧都会产生：`sub` 出的字符串（瓦片数据 4 KB × k）、临时表（4096 元素 × k）。

- 临时表用完立刻置 `nil`，不要放进任何长生命周期的表里。
- `prev` 每帧整体替换（旧串变垃圾），不要逐瓦片原地改它。
- 禁止每帧 `table.concat` 建大字符串再丢掉 **多次**；一次可以。
- 目标：单帧峰值分配 < 100 KB。

## 6. 启动与配置

沿用上一代的「纯数据配置文件」思路（`player.cfg` 是 `textutils.serialise` 的表，**不带 `return`**）：

```lua
-- /wall.cfg
{ url = "wss://example.com/play?token=xxx&region=auto",
  name = "wall1",
  role = "render",        -- render | master
  region = { 320, 0, 320, 180 },   -- 可选：不给则由 HELLO 下发
  log = true }
```

- `startup.lua` 只做一件事：跑 `/wall.lua`。
- 服务器是权威：`HELLO` 可以**覆盖**本地 `region`，避免手抄坐标出错。第一版建议**完全由服务器下发**。

## 7. 自检与日志

必须原生支持「不知道哪坏了」时的定位：

| 日志行 | 内容 | 何时 |
|---|---|---|
| `boot` | 电脑 id、hologram 是否存在、`getMaxBufferSize`、region | 启动 |
| `hello` | 协议版本、wall 尺寸、region、fps | 收到 HELLO |
| `frame` | 每 150 帧：`seq gap`、`ms`（解码）、`tiles`、`bytes` | 周期 |
| `slow` | 单帧解码 > 40 ms 时打一行（含瓦片数） | 触发时 |
| `err` | 任何 `pcall` 失败 | 即时 |

`seq` 不连续要能区分两种情况：**服务器跳帧**（正常，`DROP_OK`）与**自己漏消息**（异常，需请求重连）。

## 8. 失败与恢复

| 情况 | 处理 |
|---|---|
| ws 断开 | 2 s 后重连，重连时**丢弃 `prev`**（服务器会重发 KEY 帧） |
| 单帧解析越界（码流损坏） | 丢弃该帧、断开重连（不要带病继续画） |
| `blit` 报错 | 重新 `peripheral.find("hologram")`；连续 3 次失败则重启电脑（`os.reboot()`） |
| 长时间没收到任何消息 | 30 s 后主动断开重连 |
