# 02 · 解码预算与编解码器

> 本文是全项目的地基。所有设计都从这里的数字推出来。
> **2026-11-15 修订**：反编译 hologram 外设后发现运动补偿可以用 Java 侧的帧缓冲拷贝完成，
> 成本模型与初稿完全不同；同时第一版改为**单机负责整块 640×360**。
> 见 [`adr/0006`](adr/0006-MV用帧缓冲拷贝.md)、[`adr/0007`](adr/0007-一块全息屏只能接一台电脑.md)。

## 1. 实测：CC 的 Lua 有多快

来源：`computer/75/probe3.log`（真机，VoidPower hologram，每像素 1 字节）

| 分辨率 | 像素 | 字节串→表（16 个/批） | blit | 合计（含 sync） |
|---|---|---|---|---|
| 128×72 | 9216 | 1 ms | 1 ms | ~3 ms |
| 192×108 | 20736 | 3 ms | 3 ms | ~7 ms |
| 256×144 | 36864 | 6 ms | 5 ms | ~11 ms |
| **320×180** | **57600** | **10 ms** | **8 ms** | **~18 ms** |

同一组数据的另一列：`perByte`（每次只取 1 字节）320×180 要 **31 ms**——比批取慢 3 倍。

推导出的常量：

| 量 | 值 | 推导 |
|---|---|---|
| Lua 侧「串→表」 | **≈0.17 µs/像素** | 10 ms / 57600 |
| `blit`（Java 侧） | **≈0.14 µs/像素** | 8 ms / 57600 |
| **RAW 像素端到端** | **≈0.31 µs/像素** | 两者相加 |

## 2. 从字节码看为什么 `blit` 必然是这个价

`P_HologramPeripheral.blit` 的内层循环（反编译自 `void_power-1.0.7.fix2.jar`）：

```
map.containsKey(Double.valueOf(idx))   ← ① 装箱 + 哈希
map.get(Double.valueOf(idx))           ← ② 又一次装箱 + 哈希
check8BitColor(...)                    ← ③ 每次范围检查
```

再加 CC 把整个 Lua 表 marshalling 成 `Map` 的一次性 O(n) 拷贝。
**这是 Java 侧的开销，Lua 写得再好也省不掉。**
另外 `blit` 只接受 `table`（`IArguments.getTable(4)`），**不接受字符串**。

## 3. 决定性发现：MV 不需要 Lua

`blitFrameBufferArea(ax, ay, bx, by, bw, bh, bufferId [, mode])` 是 **纯 Java 的
`baload`/`bastore` 逐字节拷贝**：

- 没有装箱、没有哈希、没有 Lua 表；
- `bufferId = -1` 表示**显示缓冲**；`activateFrameBuffer(-1)` 切回显示缓冲；
- `mode=0` 覆盖，`mode=1` 只复制 `(pixel & 3) != 0` 的像素。

⇒ **运动补偿 = 一次 Java 调用**，几千像素只花几微秒，而不是 1 ms 量级。

**于是成本模型变成：**

> **每帧成本 ∝ 该帧「新露出」的像素数，与运动量无关。**

这才是视频编码该有的形状：平移镜头（MV 覆盖绝大部分）几乎免费，只有遮挡与新内容才付钱。

## 4. 三种操作的最终成本

| 操作 | 实现 | 成本 |
|---|---|---|
| **SKIP** | 什么都不做（显示缓冲保持上一帧） | **0** |
| **MV** | `blitFrameBufferArea(...)`，Java memcpy | **~5–15 µs/块**（调用开销，与块大小基本无关） |
| **RAW** | `blit(x,y,w,h,table)` | **0.31 µs/像素**（256 px 的块 ≈ 0.08 ms；4096 px ≈ 1.3 ms） |

20 fps ⇒ 50 ms/帧。固定开销：`sync()` 要 `arraycopy(230400)` + zlib 压整个缓冲 ≈ **1–2 ms**。

## 5. 块大小怎么选（640×360）

`⌈640/B⌉ × ⌈360/B⌉` 块，每帧成本：

```
t ≈ N × 10µs  +  R × 0.31µs  +  2ms(sync)
```

640×360 = 230400 像素。按「典型内容有 10% 像素需要 RAW」（= 23040 px = 7.1 ms）估算：

| 块 | N（40×23 网格下的实际值） | MV 开销 | 典型 RAW | 典型合计 |
|---|---|---|---|---|
| 64×64 | 10×6 = **60** | 0.6 ms | 7.1 ms | **~9.7 ms** |
| 32×32 | 20×12 = **240** | 2.4 ms | 7.1 ms | **~11.5 ms** |
| **16×16** | 40×23 = **920** | 9.2 ms | 7.1 ms | **~18.3 ms** |
| 8×8 | 80×45 = **3600** | 36 ms | 7.1 ms | ~45 ms ❌ |

**关键**：上表的 RAW 比例是**假设值**，实际上面越细的块，RAW 的浪费越少
（一个 16 px 的小物体在 64×64 网格里要重发 4096 像素，在 16×16 网格里只需 256）。
所以 16×16 的真实典型值会比 18.3 ms 更低，而 64×64 的真实典型值会更高。

⇒ **选 16×16**：

- 典型 ~18 ms，预算 50 ms，余量 2.7 倍；
- 运动/遮挡粒度接近 MPEG-1，画质明显好于 32×32；
- 最坏情况（全 RAW）71.4 ms + sync ≈ **74 ms**，掉到 13 fps——用 §6 的渐进刷新解决；
- 若实测单次 `blitFrameBufferArea` 超过 **20 µs**，退回 32×32（240 × 20 µs = 4.8 ms，仍可行）。

> 块网格用 `ceil`，最后一行/列会被 hologram 自己 clamp 到缓冲边界，
> 不需要特殊处理（`blit` 与 `blitFrameBufferArea` 都会 clamp）。

## 6. 渐进刷新（解决「全 RAW 帧」）

场景切换/seek 时整帧 230400 像素全变 ⇒ 一帧 74 ms，会掉帧。

**做法**：把这种帧拆成 `k` 个连续帧，每帧只重发 `1/k` 的块（都是 RAW），
其余块跳过（保留旧内容）。屏幕表现为「分块刷新」而不是「卡一下」。

| k | 每帧 RAW 像素 | 每帧成本 | 结果 |
|---|---|---|---|
| 1 | 230400 | ~74 ms | 13 fps，卡顿可见 |
| **2** | 115200 | ~39 ms | 20 fps 勉强 |
| **3** | 76800 | ~27 ms | 20 fps 稳 |
| 4 | 57600 | ~21 ms | 20 fps 宽裕，但「刷新」更久（4 帧 = 200 ms） |

⇒ **k=3**。刷完一整屏 150 ms，肉眼是一次很快的「擦入」，不是卡顿。

注意：渐进刷新期间**不用 MV**（prev 处于新旧混合状态），
每帧结束仍然把显示缓冲存进 prev，序列结束后 prev 自然等于新帧。

## 7. 仍然不能做的事（成本不受 §3 的改善影响）

| 不能做 | 原因 |
|---|---|
| DCT / 小波变换 | 逐系数运算，O(像素×k) |
| 熵编码（算术/哈夫曼） | 逐比特解码，每符号几十次 Lua 迭代 |
| 亚像素运动补偿 | 需要插值 ⇒ 逐像素运算 |
| 环路滤波 / 去块 | 逐像素抽头 |
| 帧内方向预测 | 逐像素 |
| **标准 VP8/H.264/VP9/AV1** | 以上全部都要 ⇒ 见 [`adr/0002`](adr/0002-不用纯Lua-VP8.md) |

**MV 免费只解决了「运动」，没解决「残差」。** 所以码流里**没有残差**：
一块要么不动、要么整块平移、要么整块重发。这也是块不能太大的原因——
太大时「局部变化」会强迫整块 RAW。

## 8. 编码器必须与解码器**位精确一致**

码流是自定义的，编码器必须能**逐像素复现解码结果**，否则调试无从下手。

规范：

1. 编解码共用同一份整数算法描述，像素路径禁止 float。
2. 编码器每写一帧，自己走一遍解码（`decode(encode(f))`），与预期帧逐字节比对；不一致即停机。
3. MV 的越界规则必须严格一致：编码器不得产生源矩形超出区域的 MV。

## 9. 带宽（640×360 单流，16×16 块）

| 场景 | RAW 像素/帧 | 每帧字节 | 码率（20 fps） |
|---|---|---|---|
| 静止 | 0 | ~123 | **~20 Kbps** |
| 平移镜头 | ~5% (11520) | ~12 KB | **~1.9 Mbps** |
| 典型 | ~10% (23040) | ~23 KB | **~3.7 Mbps** |
| 剧烈 | ~50% (115200) | ~116 KB | ~18.5 Mbps |
| 全 intra（KEY） | 230400 | ~231 KB | 36.9 Mbps（只在切换的 1–3 帧） |

**典型的 3.7 Mbps** 对公网 VPS 完全不是问题（1 Gbps 口），真正的成本是**出口流量计费**：
按每天播 4 小时算，约 **0.5 TB/月**。

## 10. 内存

| 项 | 大小 | 说明 |
|---|---|---|
| 上一帧 | **0（在 Java 堆）** | 存在 framebuffer 里，不占 Lua 内存 ✅ |
| 当前帧 | **0** | 直接画进显示缓冲 ✅ |
| RAW 块的临时表 | 256 项 × ~32 B | 用完即弃 |
| 收包字符串 | ≤ 48 KB/片 | 一帧可能 3–5 片，但可边收边解 |

⇒ **Lua 内存压力极小**。初稿里「维护 57.6 KB `prev` + 大量临时表」的负担完全消失。

## 11. 每帧的 `sync` 是固定成本

`HologramTE.fillSendBufferAndMarkDirty` 做 `arraycopy(w×h)`，
`HoloSyncData.compress` 再用 **zlib `Deflater` 压整个缓冲**（640×360 = 230400 B）。

- 每帧只调用**一次** `sync()`；
- 估算 1–2 ms 服务端 CPU，20 fps 下占 2–4%；
- 无法只压变化区域（API 不支持）。

## 12. 预算总表（单机，640×360，16×16 块，20 fps）

| 阶段 | 典型 | 最坏（全 RAW） |
|---|---|---|
| 收包 + 解析 bitmap | ~1 ms | ~1 ms |
| MV 调用（920 块的上界） | 2 ms | 0 ms |
| RAW 建表 + blit | 7 ms | 71 ms |
| display→prev 拷贝 | 0.1 ms | 0.1 ms |
| `sync()`（zlib） | 1–2 ms | 1–2 ms |
| **合计** | **~11–18 ms** | **~74 ms** |
| **可用（20 fps）** | 50 ms ✅ 余量 3 倍 | 50 ms ❌ 用渐进刷新 |
