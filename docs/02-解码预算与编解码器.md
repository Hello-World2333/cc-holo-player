# 02 · 解码预算与编解码器

> 本文是全项目的地基。所有设计都从这里的数字推导出来。

## 1. 实测：CC 的 Lua 有多快

来源：`computer/75/probe3.log`（真机，VoidPower hologram，每像素 1 字节）

| 分辨率 | 像素 | 字节串→表（16 个/批） | blit | 合计（含 sync） |
|---|---|---|---|---|
| 128×72 | 9216 | 1 ms | 1 ms | ~3 ms |
| 192×108 | 20736 | 3 ms | 3 ms | ~7 ms |
| 256×144 | 36864 | 6 ms | 5 ms | ~11 ms |
| **320×180** | **57600** | **10 ms** | **8 ms** | **~18 ms** |

同样数据的另一列：`perByte`（每次 `string.byte` 只取 1 个）320×180 要 **31 ms**——比批取慢 3 倍。

**由此得到的常量：**

| 量 | 值 | 推导 |
|---|---|---|
| 每像素「串→表」 | **≈0.17 µs** | 10 ms / 57600 |
| 每像素 blit | **≈0.14 µs** | 8 ms / 57600 |
| 一次 `string.byte(s,i,i+15)` + 16 次表写入 | **≈2.8 µs** | 10 ms / 3600 批 |
| Lua 简单循环迭代 | **≈0.3×10⁶ /s** | 同上 |

> 这不是「Lua 慢」的泛泛之谈：**这台机器的预算是可算的**。

## 2. 每帧预算

目标 20 fps ⇒ **50 ms/帧**。扣掉固定开销：

| 项 | 成本 |
|---|---|
| 事件循环 + ws 收包 + 解析 | 2–5 ms |
| 本帧要重绘的瓦片（转表 + blit） | 见下 |
| **留给「解码逻辑」的余量** | **≈20–30 ms ≈ 7000–10000 次迭代** |

关键结论：

> **解码器必须做到 O(块)、每像素至多一次表写入。**
> 任何「每像素若干次 Lua 运算」的解码（变换、滤波器、逐像素预测）都会直接超预算 10–100 倍。

而且：**只有变化的瓦片才花钱**。不变的瓦片不转表、不 blit、成本为 0。
所以码流里运动补偿（MV）的**主要收益不是省带宽，是让「需要重绘的瓦片数」变少**。

## 3. 为什么不能解「真 VP8」

VP8 解码的每一步都是逐比特/逐系数的 Lua 循环：

| VP8 环节 | 320×180 一帧的量 | 是否可 C 化 |
|---|---|---|
| 布尔算术解码（每个符号读若干 bit，带概率查表与重归一化） | 每宏块 ≈24 个 4×4 块 × 平均 8 个 token ≈ 200 个符号 | ❌ 纯 Lua 循环 |
| 反量化 + 反变换（iDCT/iWHT） | ≈240 宏块 × 24 块 = 5760 次 | ❌ |
| 帧内/帧间预测（含 4×4 边界的 9 种模式） | 每次预测 16–256 次像素运算 | ❌ |
| 环路滤波 | 每个宏块边界若干抽头 | ❌ |
| 运动补偿拷贝 | **这一项是快的** | ✅ 取决于实现 |

粗算（按 §1 的 2.8 µs/迭代）：

```
240 宏块 × (200 符号 × ≈20 迭代/符号 + 24 块 × ≈40 迭代 iDCT + 预测/滤波 ≈500)
= 240 × (4000 + 960 + 500)
≈ 1.3×10⁶ 迭代
× 2.8 µs  ≈  3.6 秒/帧   →  0.3 fps
```

要跑到 20 fps 需要**快 70 倍**。降到 160×90 也只有 ~1.5 fps。
结论：**纯 Lua 解真 VP8 不可行**，不是优化问题，是量级问题。详见 [`adr/0002`](adr/0002-不用纯Lua-VP8.md)。

其它标准编码器同理（H.264/VP9/AV1 只会更重）。唯一可行的是**在 CC 里加原生解码器**（写 mod），
但那违背「MC 机器零新依赖」的目标，不在本期范围。

## 4. 可行的编码族：**块级复制 + 少量新像素**

把「解码」压缩成 CC 做得动的三种操作：

| 操作 | CC 成本 | 说明 |
|---|---|---|
| 跳过（本块与上一帧相同 / 用同一份内容） | ~0 | 不转表、不 blit |
| 从上一帧按整数位移 (dx,dy) 拷一块 | 每行一次 `string.sub` + 拼表 | O(块高)，C 侧 |
| 新像素（本块 literal） | 0.17 µs/px | 只能整块替换 |

**没有**变换、没有残差、没有亚像素、没有滤波——这三样都会把成本从 O(块) 推到 O(像素×若干)。

### 4.1 两种 profile

| | **P1 · 64×64 瓦片** | **P2 · 16×16 宏块** |
|---|---|---|
| 分区 | 640×360 → 10×6 = 60 瓦片，每 quadrant 15 块 | 40×23 = 920 宏块，每 quadrant 240 块 |
| 运动粒度 | 64 px（整块平移，pan 效果极好，局部运动差） | 16 px（接近 MPEG-1 的观感） |
| 解码成本（全帧变化） | 15 块 × (64 行 sub + 0.7 ms 转表 + 0.6 ms blit) ≈ **22 ms** | 240 块 × (16 行 sub + 转表 + blit) ≈ **31 ms** |
| 解码成本（典型 30% 变化） | ~7 ms | ~10 ms |
| 每帧原始字节（全 intra） | 57600 B = 9.2 Mbps@20 | 245 KB = **39 Mbps**（必须靠 MV 压下来） |
| 实现复杂度 | 低（与上一代 tile 结构同构） | 中（需要宏块模式与 MV 搜索） |

**建议**：先做 **P1** 跑通全链路（解码器、同步、拼接、部署），再升级到 P2。
P1 的观感在「摄像机平移/整体缩放」类内容（MV 类视频很常见）上已经可用；固定机位对话类镜头会看到 64 px 的块状。

### 4.2 码流里刻意**不要**的东西

- ❌ 算术/哈夫曼式的逐比特熵编码 → 用**字节对齐的 varint**
- ❌ 4×4/8×8 DCT 残差 → 残差只能整块重发
- ❌ 亚像素运动补偿（需要插值 = 每像素运算）
- ❌ 环路滤波 / 去块效应
- ❌ 帧内预测（JPEG 那种逐像素方向预测）
- ✅ 帧间整数运动矢量（整块复制）
- ✅ 块内「与上一帧同位置相同」直接跳过
- ✅ 帧级「整帧不变」跳过（静止画面成本为 0）

## 5. 编码器必须与解码器**位精确一致**

因为码流是自定义的，编码器必须能**逐像素复现解码结果**，否则调试无从下手。

规范：

1. 编解码共用**同一份整数算法描述**（文档 + 后续的参考实现），不允许 float 参与像素路径。
2. 编码器每写一帧，自己走一遍解码（`decode(encode(f))`），与预期帧逐字节比对；不一致就报错停机。
3. `tools/` 里要有 `conformance`：一组固定输入 → 固定码流 → 固定输出，用于回归。

## 6. 带宽目标

| 场景 | 每 quadrant | 4 块合计 |
|---|---|---|
| P1 · 静态/轻微运动 | 0.2–0.6 Mbps | 0.8–2.4 Mbps |
| P1 · 典型 MV | 0.8–2 Mbps | 3–8 Mbps |
| P1 · 极限（全 intra） | 9.2 Mbps | 37 Mbps |
| P2 · 典型 MV | 0.5–1.5 Mbps | 2–6 Mbps |

公网可行性：wss 单消息 < 128 KB，我们按 4–8 KB 分片；持续 3–8 Mbps 对一台 VPS 是小负载。
**真正需要担心的是 VPS 的出口带宽计费**，不是 CC 端。

## 7. 先做的一个实验（省一半算力）

`hologram.blit(x, y, w, h, pixels)` 的 `pixels` 在官方文档里是**表**（`{0..255, ...}`），
上一代的 `render.lua` 也是先 `buildTable()` 再 blit。

**但如果它接受 raw 字节串**，每像素 0.17 µs 的转表成本直接消失，预算翻倍（320×180 从 18 ms 降到 8 ms）。

⇒ 这是一个**必须先测**的探针（见 `docs/06` 第 1 条）。测法：同一个 64×64 瓦片，分别传 table 与 string，比较耗时与是否报错。

## 8. 内存

| 项 | 大小 |
|---|---|
| 上一帧（字符串，1 B/px） | 320×180 = 57.6 KB / quadrant |
| 当前帧表（若常驻） | 57600 个整数 ≈ 0.5–1 MB ⚠️ |
| 瓦片缓存（每块一张表） | 15 × 4096 ≈ 0.7 MB ⚠️ |

⇒ **不要**常驻大表：每帧现转现 blit、用完即弃。只保留 `prev` 字符串（57.6 KB）作为 MV 的拷贝源。
这一条直接影响 `docs/03` 的实现形态。
