# 02 · 解码预算与编解码器

> 本文是全项目的地基。所有设计都从这里的数字推出来。
> **2026-11-15 修订**：反编译 hologram 外设后发现「运动补偿可以用 Java 侧的帧缓冲拷贝完成」，
> 成本模型与初稿完全不同。见 [`adr/0006`](adr/0006-MV用帧缓冲拷贝.md)。

## 1. 实测：CC 的 Lua 有多快

来源：`computer/75/probe3.log`（真机，VoidPower hologram，每像素 1 字节）

| 分辨率 | 像素 | 字节串→表（16 个/批） | blit | 合计（含 sync） |
|---|---|---|---|---|
| 128×72 | 9216 | 1 ms | 1 ms | ~3 ms |
| 192×108 | 20736 | 3 ms | 3 ms | ~7 ms |
| 256×144 | 36864 | 6 ms | 5 ms | ~11 ms |
| **320×180** | **57600** | **10 ms** | **8 ms** | **~18 ms** |

同一组数据的另一列：`perByte`（每次 `string.byte` 只取 1 个）320×180 要 **31 ms**——比批取慢 3 倍。

推导出的常量：

| 量 | 值 | 推导 |
|---|---|---|
| Lua 侧「串→表」 | **≈0.17 µs/像素** | 10 ms / 57600 |
| `blit`（Java 侧） | **≈0.14 µs/像素** | 8 ms / 57600 |
| **RAW 像素端到端** | **≈0.31 µs/像素** | 两者相加 |

## 2. 从字节码看为什么 `blit` 必然是这个价

`P_HologramPeripheral.blit` 的内层循环（反编译自 `void_power-1.0.7.fix2.jar`）：

```
map.containsKey(Double.valueOf(idx))   ← ① 装箱 + 哈希
map.get(Double.valueOf(idx))           ← ② 又一次装箱 + 哈希
check8BitColor(...)                    ← ③ 每次范围检查
```

再加 CC 把整个 Lua 表 marshalling 成 `Map` 的一次性 O(n) 拷贝。
**这是 Java 侧的开销，Lua 写得再好也省不掉。**

## 3. 决定性发现：MV 不需要 Lua

`blitFrameBufferArea(ax, ay, bx, by, bw, bh, bufferId [, mode])` 是 **纯 Java 的
`baload`/`bastore` 逐字节拷贝**：

- 没有装箱、没有哈希、没有 Lua 表；
- `bufferId = -1` 表示**显示缓冲**；`activateFrameBuffer(-1)` 切回显示缓冲；
- `mode=0` 覆盖，`mode=1` 只复制 `(pixel & 3) != 0` 的像素（alpha 键控）。

⇒ **运动补偿 = 一次 Java 调用**，4096 像素只花几微秒，而不是 1.3 ms。

**于是成本模型变成：**

> **每帧成本 ∝ 该帧「新露出」的像素数，与运动量无关。**

这才是视频编码该有的形状：平移镜头（MV 覆盖绝大部分）几乎免费，只有遮挡与新内容才付钱。

## 4. 三种操作的最终成本

| 操作 | 实现 | 成本 |
|---|---|---|
| **SKIP** | 什么都不做（显示缓冲保持上一帧） | **0** |
| **MV** | `blitFrameBufferArea(...)`，Java memcpy | **~5–15 µs/块**（调用开销，与块大小无关） |
| **RAW** | `blit(x,y,w,h,table)` | **0.31 µs/像素**（400 px 的块 ≈ 0.12 ms；4096 px ≈ 1.3 ms） |

20 fps ⇒ 50 ms/帧。扣掉事件循环、收包、`sync`（zlib 压缩整块缓冲 1–2 ms），
**留给块操作约 30–40 ms。**

## 5. 块大小怎么选

设区域 `W×H`，块边长 `B`，块数 `N = ⌈W/B⌉·⌈H/B⌉`，每帧 RAW 像素数 `R`：

```
t ≈ N × 10µs  +  R × 0.31µs
```

320×180 区域的几种选择（假设「典型内容」有 10% 的像素需要 RAW）：

| 块 | N | MV 开销（全 MV 上界） | RAW 开销（10% = 5760 px） | 合计 |
|---|---|---|---|---|
| 64×64 | 15 | 0.15 ms | 1.8 ms | **~2 ms** |
| **32×32** | 60 | 0.6 ms | 1.8 ms | **~2.4 ms** |
| **16×16** | 240 | 2.4 ms | 1.8 ms | **~4.2 ms** |
| 8×8 | 960 | 9.6 ms | 1.8 ms | ~11.4 ms |

⇒ **32×32 或 16×16 是甜点。** 16×16 的运动粒度已经接近 MPEG-1，成本仍远低于预算。

**第一版建议 16×16**：
- 运动补偿精细（对平移/摇镜/局部运动都够用）；
- 4 ms 的解码成本留下 10 倍余量，足以应付「整帧都变」的最坏情况
  （全部 RAW = 57600 px × 0.31 µs = **17.9 ms**，仍在预算内）；
- 若实测调用开销高于 10 µs，退回 32×32 只需改一个常量。

> 块网格用 `ceil(W/B) × ceil(H/B)`，最后一行/列会被 hologram 自己的裁剪逻辑截掉
> （`blit` 与 `blitFrameBufferArea` 都会 clamp 到缓冲边界），不需要特殊处理。

## 6. 仍然不能做的事（成本不受 §3 的改善影响）

| 不能做 | 原因 |
|---|---|
| DCT / 小波变换 | 逐系数运算，O(像素×k)，回到 0.17 µs/像素的数量级之上 |
| 熵编码（算术/哈夫曼） | 逐比特解码，每符号几十次 Lua 迭代 |
| 亚像素运动补偿 | 需要插值 ⇒ 逐像素运算 |
| 环路滤波 / 去块 | 逐像素抽头 |
| 帧内方向预测 | 逐像素 |
| **标准 VP8/H.264/VP9/AV1** | 以上全部都要 ⇒ 见 [`adr/0002`](adr/0002-不用纯Lua-VP8.md) |

**MV 免费只解决了「运动」，没解决「残差」。** 所以码流里**没有残差**：
一块要么整块不动、要么整块平移、要么整块重发。
这也是为什么块不能太大——太大时「局部变化」会强迫整块 RAW。

## 7. 编码器必须与解码器**位精确一致**

码流是自定义的，编码器必须能**逐像素复现解码结果**，否则调试无从下手。

规范：

1. 编解码共用同一份整数算法描述，像素路径禁止 float。
2. 编码器每写一帧，自己走一遍解码（`decode(encode(f))`），与预期帧逐字节比对；不一致即停机。
3. MV 的越界规则必须严格一致：**编码器不得产生源矩形超出区域的 MV**；
   解码器遇到越界的 MV 视为 no-op（`blitFrameBufferArea` 的 clamp 行为），
   编码器在建模时必须采用同一规则。

## 8. 带宽目标（16×16 块）

每帧需传输的是 **RAW 像素 + 每块的模式/MV 向量**：

| 场景 | RAW 像素/帧（320×180 区域） | 码率（20 fps） |
|---|---|---|
| 静止 | 0 | **~0**（只有帧头） |
| 平移镜头 | ~5%（2880 px） | ≈ 460 Kbps |
| 典型 | 10%（5760 px） | ≈ 920 Kbps |
| 剧烈/场景切换 | 50%（28800 px） | ≈ 4.6 Mbps |
| 全 intra（理论最坏） | 100%（57600 px） | ≈ 9.2 Mbps |

4 个象限合计：典型 **3.7 Mbps**，最坏 37 Mbps（只在场景切换的一两帧出现）。
公网 VPS 完全承受得住，**真正的成本项是出口流量计费**。

## 9. 内存

| 项 | 大小 | 说明 |
|---|---|---|
| 上一帧 | **0（在 Java 堆）** | 存在 framebuffer 里，不占 Lua 内存 ✅ |
| 当前帧 | **0** | 直接画进显示缓冲 ✅ |
| RAW 块的临时表 | B² × ~32 B | 16×16 时 256 项，用完即弃 |
| 收包字符串 | ≤ 64 KB | 一帧一条消息 |

⇒ 相比初稿（Lua 侧维护 57.6 KB 的 `prev` + 大量临时表），**Lua 内存压力几乎消失**。

## 10. 每帧的 `sync` 是固定成本

`HologramTE.fillSendBufferAndMarkDirty` 做 `arraycopy(w×h)`，
`HoloSyncData.compress` 再用 **zlib `Deflater` 压整个缓冲**（640×360 = 230400 B）。

- 每帧只应调用**一次** `sync()`（由 master 调）；
- 估算 1–2 ms 服务端 CPU，20 fps 下占 2–4%；
- 无法只压变化区域（API 不支持）。

⚠️ 这里有一个**未解风险**：若多台电脑共享同一个 hologram 外设实例，
它们的 `activateFrameBuffer` / `sync` 可能互相干扰。见 [`adr/0006`](adr/0006-MV用帧缓冲拷贝.md) 的「未解」一节。
