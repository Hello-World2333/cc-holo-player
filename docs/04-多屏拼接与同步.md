# 04 · 多屏拼接与同步

## 1. 物理事实：一张缓冲，分区写入

VoidPower 的 hologram 只有一个显示帧缓冲，上限 `getMaxBufferSize() = 393216` 像素。

| 墙尺寸 | 像素 | 能放进一块 hologram？ |
|---|---|---|
| 640×360（2×2，本版） | 230400 | ✅ |
| 960×540（3×3） | 518400 | ❌ 需要 2 块以上 |

所以本版**只要一块 hologram**：4 台电脑各自 `blit` 到**全局坐标**的不同矩形，
同屏叠加成一张画。这不是「拼图」，是「多人协作画同一张画布」。

```
    x: 0        320        640
 y=0  ┌──────────┬──────────┐
      │  #A      │  #B      │   #A: region 0,0,320,180   → blit(0,0,…)
 y=180├──────────┼──────────┤   #B: region 320,0,…       → blit(320,0,…)
      │  #C      │  #D      │   #C: region 0,180,…       → blit(0,180,…)
 y=360└──────────┴──────────┘   #D: region 320,180,…     → blit(320,180,…)
```

**每台电脑都要 `resize(640, 360)`**（不是 `resize(320,180)`）：`resize` 改的是整块缓冲的尺寸，
`blit` 的坐标是缓冲坐标。

## 2. 分区与码流的关系

每台电脑收到的是**自己 region 的独立码流**（见 `docs/01`）。这样：

- 解码量与区域面积成正比（320×180 正好是 20 fps 的稳妥档）；
- 各机互不等待，弱机慢只影响自己那块；
- 代价：运动矢量不能越过分区边界（`docs/01` §4.1 要求源矩形完全落在区域内）
  ⇒ 边界附近的平移会被迫用 RAW 重发，画质与码率都略有损失。20 块宽的区域里，边界只占约 5%。

> 若将来想省一道编码，也可以让 4 台解同一个 640×360 码流、各用一部分——但解码量 ×4，直接超预算。**不采用。**

## 3. 同步：为什么需要、怎么做到

CC 上每台电脑的 `blit` 是**异步**的：像素写进缓冲后，要等某台电脑调用 `h.sync()` 才真正显示。
若 4 台各画各的、各自 sync，就会出现「上半屏是新帧、下半屏还是旧帧」——即**水平撕裂**。

上一代的解法（已跑通 640×360）：**同一时刻只允许一帧在飞**，全部画完后由 master 统一 sync。

### 3.1 本版的时序

```
Node                #A..#D（各自 ws）           master
 │   FRAME(seq=N) ──▶ 各机解码 + blit
 │                                    ────────▶  ack(N)  via fabric
 │  （可选）继续推 N+1                         │
 │                                    ◀────────  4 个 ack 齐 → h.sync()
 │                                    ────────▶  go(N+1) via fabric
```

两种节奏策略，**第一版建议 (a)**：

**(a) 服务器严格锁步**
- Node 收到某 room 的 4 台「全部 ack N」后才发 N+1。
- 简单、天然不撕裂；缺点是慢机拖累全墙（与上一代相同）。
- Node 需要知道 4 台的身份：靠 `token` 前缀 + `region` 识别。

**(b) 客户端栅栏（fabric 主导）**
- Node 只管按 fps 推帧，CC 自己用 fabric 对齐。
- 需要处理「某台落后 → 整墙等 or 丢帧」的仲裁，第一版不做。

### 3.2 用 fabric 传什么

| 消息 | 方向 | 内容 |
|---|---|---|
| `ack` | 渲染机 → master | `{t="ack", n=seq}` |
| `go` | master → 渲染机 | `{t="go", n=seq}`（可选，见 (b)） |
| `state` | master → 渲染机 | 播放/暂停（也可由 Node 广播） |

fabric 的额度（`bulkTokensPerTick=8`、`sendTokensPerTick=32`、`ingressDrainPerTick=32`）
对「每帧 4 条 ack」是**完全够的**：20 fps × 4 = 80 条/秒，摊到每 tick 约 4 条，远低于 32。

> 注意：`fabricSend` / `fabricBroadcast` **只能发给电脑**（hub / 存储卷收到也处理不了），
> 且对方必须**开机**（关机的电脑不消耗事件额度，消息直接不投递）。
> 广播的返回值是「成功投递数」，不等于「已处理」，所以 ack 必须由接收方显式回发。

### 3.3 master 是谁

| 方案 | 电脑数 | 优点 | 缺点 |
|---|---|---|---|
| **A. 渲染机里选一台当 master** | 4 | 省一台 | master 自己要解码，sync 时机被自己的解码延迟影响 |
| B. 独立 master 机 | 5 | 时序干净、可跑 GUI/日志 | 多一台；它也要连 ws（只收 ack 指令） |

**第一版建议 A**（`HELLO.flags` 的 `bit0` 指定），因为解码只要 5–10 ms，不影响 sync 时机。

## 4. 丢帧与追赶

必须能应对「某台一时卡住」：

1. 渲染机收到 `DROP_OK` 帧时可以直接跳过不画（只回 ack），让墙保持流畅。
2. master 等待 ack 有超时（例如 200 ms）：超时就**不等了**，直接 sync 并让慢机后续丢弃直到追上。
3. Node 侧保留「上一帧的 KEY 帧」；慢机重连或请求重同步时从 KEY 开始。

> 上一代的 watchdog：1.2 s 无进展就回退到「所有机都已确认的最小帧」。本版沿用这个思路，
> 但判定阈值要按 20 fps 收紧（200–300 ms）。

## 5. 扩展到 3×3 / 更大

- **像素数**：960×540 = 518400 > 393216 ⇒ 必须拆成 **2 块 hologram**（例如 2×1 的屏），
  每块屏一个共享缓冲、一组渲染机。跨屏同步 = 两组的 master 再互相同步（多一层）。
- **电脑数**：9 台渲染机 + 2 台 master。
- **码流**：9 个独立分区流，或按「屏」组织。
- 这些都不改码流格式，只改 `region` 分配与同步层级 ⇒ `docs/01` 的协议**不需要为拼接扩展**。

## 6. 对齐的坑

| 坑 | 说明 |
|---|---|
| 坐标是**全局缓冲坐标** | `blit` 用 `region_x/y`，不是 `0,0` |
| 尺寸必须整除 | 640/320、360/180 整除；若换 3×3，640/3 不整除 → 会有 1 px 缝隙或重叠，需要**显式定义**（建议让最后一块多 1 px） |
| 每台各占一个 framebuffer | 16 个槽位，4 台各占 1 个给 `prev`；若外设实例是共享的，`releaseAllFrameBuffer` 会误清别人（见 `06` §1） |
| 每台都要 `resize(640,360)` | 少 resize 的那台会画到不存在的区域 |
| `sync` 只能一台调 | 多台各自 sync 会互相打断，表现为画面闪烁 |
| 一台掉线全墙停 | 因为锁步；需要 §4 的超时机制 |
