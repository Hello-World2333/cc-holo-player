# 04 · 屏幕拼接与同步

> 第一版**只有一块屏、一台电脑**，所以本文前半部分讲「为什么不需要拼接」，
> 后半部分（§4 起）讲真要做多屏时怎么办。

## 1. 物理事实：一块 hologram 只有一张缓冲，也只有一个外设实例

| 事实 | 值 | 出处 |
|---|---|---|
| 单块缓冲像素上限 | **393216** | `HoloFrameBuffer.resize` 的 `ldc 393216` |
| 外设实例 | **每方块一个**，懒加载后缓存在 TE 字段 | `HologramTE.getPeripheral()` |
| 多电脑接入 | 支持（`computers` 是 `Set`），但**不隔离任何状态** | `P_HologramPeripheral.attach` |
| 「当前激活缓冲」 | `HoloFrameBufferManager` 的**单个字段** | `currentActivated` |

⇒ **640×360 = 230400 像素，一块屏装得下，一台电脑画得完。** 第一版到此为止。

⇒ 更高分辨率（如 960×540 = 518400）**装不下一块屏**，必须多块屏；
多块屏必然是**每块屏一台电脑**（ADR-0007）。

## 2. 第一版：不需要同步，因为没有第二个参与者

上一代用 fabric 做 ack 栅栏：4 台各画一块，全部画完才由 master `sync()`。
现在只有一台电脑：

```
收帧 → 解码 → 画进显示缓冲 → 存进 prev → sync() → 回 ACK
```

帧序天然一致，不存在「半屏新半屏旧」。**fabric 在第一版一行代码都不用。**

这也意味着：`ACK` 的唯一作用是**流控**（1 帧在飞），不是同步。

## 3. 单机的时间预算

| 阶段 | 典型 | 全 RAW |
|---|---|---|
| 收包 + 解析 | ~1 ms | ~1 ms |
| MV（920 块上界） | 2 ms | 0 |
| RAW 建表 + blit | 7 ms | 71 ms |
| display→prev | 0.1 ms | 0.1 ms |
| `sync()`（zlib 压 230400 B） | 1–2 ms | 1–2 ms |
| **合计** | **~11–18 ms** | **~74 ms** |

50 ms 的预算 ⇒ 典型情况有 3 倍余量。全 RAW 帧用 `docs/02` §7 的**渐进刷新**（拆 3 帧）。

## 4. 将来上多屏：两种形态

### 4.1 形态 B：每块屏一台电脑（唯一能突破 393216 的路线）

```
        ┌──────────┬──────────┐
        │ 屏0 #A   │ 屏1 #B   │   每块 hologram 有自己的
        │ 640×360  │ 640×360  │   P_HologramPeripheral 实例
        └──────────┴──────────┘   ⇒ 各自的 currentActivated
          region0    region1
```

- 每台电脑只画自己那块的**局部坐标**，不需要知道全局坐标。
- 位置对齐靠 `setOffset` / `setRotation` / `setScale`——三者都是 `@LuaFunction`，
  **可以程序化设置**，不必手工摆。
- 码流：每个 region 一条独立流（MV 不能跨屏）。`docs/01` 不需要改。
- 需要处理：
  - **接缝**：`screenScale` 是 float，可能有亚像素误差；需要实测并微调 offset。
  - **跨屏同步**：此时才需要 fabric 栅栏（见 §5）。

### 4.2 形态 H：多台电脑共享一块屏（不推荐，但可行）

若坚持「4 台各画一块、只要一块屏」，唯一安全的做法是**只有 master 做 MV**：

- 渲染机只 `blit` RAW 块（此时 `currentActivated` 恰好是显示缓冲，**不要 activate**）；
- master 承担全墙的 `blitFrameBufferArea`（从自己的 prev 读）；
- 全部 ack 齐后，master 才 `activate(prevId)` → 拷 → `activate(-1)` → `sync()`。

安全前提是 ack 栅栏保证「渲染机 ack 之后到下一帧之前不碰外设」。
好处：MV 可跨象限，压缩率更好。代价：竞态极难复现，Node 要按块而非按区域分派。

**第一版不做。**

## 5. 多屏时的 fabric 栅栏（形态 B 需要）

| 消息 | 方向 | 内容 |
|---|---|---|
| `ack` | 各屏 → master | `{t="ack", n=seq}` |
| `go` | master → 各屏 | `{t="go", n=seq}` |
| `state` | master → 各屏 | 播放/暂停 |

fabric 额度对「每帧 N 条 ack」完全够：20 fps × 4 = 80 条/秒，摊到每 tick 约 4 条，
而 `sendTokensPerTick = 32`，且 payload 十几字节不算 bulk。

> 注意：`fabricSend`/`fabricBroadcast` 只投递给**开机**的电脑，
> 返回值是「成功投递数」，不等于「已处理」⇒ ack 必须由接收方显式回发。

## 6. 对齐的坑（形态 B）

| 坑 | 说明 |
|---|---|
| 尺寸不能整除 | 640 能被 2/4/5/8/10 整除；360 能被 2/3/4/5/6/8 整除。3×3 会不整除 ⇒ 需显式定义边界（建议最后一块多 1 px） |
| 每块屏各自 `resize` | **必须是这一块屏自己的像素尺寸**，不是整墙尺寸 |
| `sync` 只能一台调 | 多台各自 sync 会互相打断，表现闪烁 |
| 接缝亚像素 | `screenScale` float 精度；需要实测微调 `setOffset` |
| 一台掉线全墙停 | 因为栅栏；需要超时（建议 200–300 ms）与丢帧追赶 |
