# cc-video-wall

CC（ComputerCraft）全息视频墙：**公网 Node 负责编码，游戏里的 CC 电脑自己解码，画到 VoidPower 的 hologram 上**。
多块屏幕可拼接成更高的分辨率。

> 状态：**已实现并在真机跑通**（2026-11-15）。两个测试片源在 CC 上实测
> **34–35 fps、34 万块/秒、0 次重同步**。
>
> | 片源（640×360 @20fps） | 时长 | 码率 | 相对源 H.264 |
> |---|---|---|---|
> | 科学-MIMI（较静） | 188 s | **0.85 Mbps** | 0.77× |
> | 洛天依雨爱（剧烈运动） | 263 s | **1.87 Mbps** | 3.1× |
>
> 上一代 rawvideo 方案是 36.86 Mbps。换算成公网出口流量：每天播 4 小时约
> **0.15–0.35 TB/月**（`docs/02` §10.1 是实测，不是估算）。
>
> 动手前请先读 [`docs/02-解码预算与编解码器.md`](docs/02-解码预算与编解码器.md)——那里有四条硬事实决定了整个项目的形态：
> ① Lua 处理像素约 0.17µs/px ② 纯 Lua 解真 VP8 要 3.6 秒/帧
> ③ **运动补偿可以走 Java 侧帧缓冲拷贝，几乎免费**
> ④ **hologram 的离屏 framebuffer 可以当瓦片仓库**，跨槽拷贝 11.3µs，比从 Lua 表绘制还便宜——
> 这是把码率再降一个数量级的关键（`docs/01` §4.3）。

## 它是什么

```
┌──────────────┐   原视频(mp4/任意)    ┌────────────────┐
│ 公网服务器    │ ────────────────────▶ │ 转码器 (离线)   │  →  .ccv 文件
│ Node         │                       └────────────────┘
│              │   wss 推码流（几十~几百 KB/s）
└──────┬───────┘
       │ 公网
┌──────▼───────────────────────────────────────────────┐
│ MC 服务器（另一台机器）——**不装任何东西**             │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐    │
│  │ CC #A   │ │ CC #B   │ │ CC #C   │ │ CC #D   │    │
│  │ 解左上一 │ │ 解右上  │ │ 解左下  │ │ 解右下  │    │
│  └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘    │
│       │  fabric（同步/控制，几字节/帧）     │         │
│       └───────────┴─────┬─────┴───────────┘         │
│                  ┌──────▼──────┐                     │
│                  │  hologram   │ 640×360 一张屏      │
│                  └─────────────┘                     │
└──────────────────────────────────────────────────────┘
```

要点：

1. **MC 那台机器零依赖**：不需要 node、不需要 ffmpeg、不需要本地代理进程。码流直接从公网进 CC 的 `http.websocket`。
2. **编码在公网、解码在 CC**：所以传的是压缩码流（**0.85–1.9 Mbps**），不是 rawvideo（37 Mbps）。
3. **fabric 只跑控制**：帧号栅栏、播放状态、按键。像素不走 fabric——fabric 每个发送机每 tick 只有 8 条大包的额度，且字符串按 UTF-16 计费（`16+2N`），实际 ≈0.58 MB/s，喂不动一块屏。
4. **多屏拼接**：画面按 quadrant 切成独立码流，各机只解自己那一块；写的是**同一张** hologram 缓冲的不同坐标。
5. **解码成本只跟「新露出的像素」有关**：上一帧存在 hologram 自己的 framebuffer 里，运动补偿由 Java 完成，Lua 只处理真正变化的块。
6. **8×8 瓦片图集**：hologram 的 16 个离屏槽（每槽 393216 字节）当瓦片仓库，出现过的
   瓦片用 3 字节位置引用。实测命中率 74%，且命中比重发**更快**（11.3µs vs 31.8µs）。

## 与已有项目的关系

- [`~/cc-holo-player`](../cc-holo-player/) 是**上一代**：单机 master + 4 台 raw 瓦片渲染机 + 宿主机 Node 实时转码，raw 走 CC 的 ws。
  本项目的区别是：**把解码搬进 CC**（因此 MC 侧零依赖、可跨公网）、**码流是压缩的**、**多屏可配**。
- 它的实测数据（全息 blit 成本、事件被吞、framebuffer 泄漏、CC ws 限额）在本仓库直接沿用，见 `docs/02` 与 `docs/03` 的引用。
- 上游模组文档：`~/worker-docs/void-power-mod/`（hologram API）、`~/worker-docs/cee-cc/`（CEE:CC 的 `cee.*`，取外设/音响用）。
